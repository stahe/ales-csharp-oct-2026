    4.1. Objetos mediante ejemplos

    4.1.1. Descripción general

    Vamos a explorar ahora la programación orientada a objetos mediante ejemplos. Un objeto es una entidad que contiene datos que definen su estado (llamados campos, atributos, etc.) y funciones (llamadas métodos). Un objeto se crea a partir de una plantilla llamada clase:

    Aquí tenemos la definición de una clase y, por lo tanto, de un tipo de datos. Cuando creamos variables de este tipo, las llamamos objetos o instancias de la clase. Una clase es, por lo tanto, una plantilla a partir de la cual se construyen objetos.

    Los miembros de una clase pueden ser datos (campos), métodos (funciones) o propiedades. Las propiedades son métodos especiales que sirven para obtener o establecer el valor de los campos de un objeto. Estos miembros pueden ir acompañados de una de las siguientes palabras clave:

    Palabra clave
    Acceso
    [private]
    Un miembro privado solo es accesible por los métodos internos de la clase. Este es el nivel de acceso predeterminado
    [public]
    Un miembro público es accesible por cualquier método, esté o no definido dentro de la clase
    [protected]
    Un miembro protegido solo es accesible por los métodos internos de la clase o de una clase derivada (véase más abajo el concepto de herencia)
    [internal]
    Un miembro interno es accesible por cualquier método dentro del mismo ensamblado (el mismo proyecto)

    En general, los datos de una clase se declaran privados, mientras que sus métodos y propiedades se declaran públicos. Esto significa que el usuario de un objeto (el programador):

    • no tendrá acceso directo a los datos privados del objeto;
    • puede llamar a los métodos públicos del objeto, incluidos aquellos que dan acceso a sus datos privados.

    La sintaxis para declarar una clase [C] es la siguiente:

    1

    public class C
{
    private private data, method or property;
    public public data, method or property;
    protected protected data, method or property;
}

    El orden en que se declaran los miembros [private], [protected] y [public] es arbitrario.

    4.1.4. El método Initialize

    ¿Cuál es el propósito del método [Initialize]? Dado que [lastName], [firstName] y [age] son miembros privados de la clase [Person], las instrucciones:

    1
2
3
4
    Person p1;
p1.firstName = "Jean";
p1.lastName = "Dupont";
p1.age = 30;

    no son válidas. Necesitamos inicializar un objeto de tipo [Person] mediante un método público. Este es el propósito del método [Initialize]. Escribiremos:

    1
2
    Person p1;
p1.Initialize("Jean", "Dupont", 30);

    La notación [p1.Initialize] es válida porque [Initialize] es de acceso público.

    4.1.5. El operador new

    Sin embargo, la secuencia de instrucciones anterior es incorrecta. La instrucción

    1
    Person p1;

    declara [p1] como una referencia a un objeto de tipo [Person]. Este objeto aún no existe y, por lo tanto, [p1] no está inicializado. Cuando escribimos a continuación [p1.Initialize("Jean", "Dupont", 30)], llamamos al método [Initialize] del objeto al que hace referencia [p1]. Sin embargo, este objeto no existe y el compilador informa el error: la variable local [p1] no tiene un valor asignado. Si escribimos:

    1
2
    Person? p1 = null;
p1.Initialize("Jean", "Dupont", 30);

    indicamos explícitamente con la palabra clave [null] que la variable [p1] aún no hace referencia a ningún objeto (el signo de interrogación en [Person?] indica que a la variable se le puede asignar [null]). El compilador emite entonces solo una advertencia (desreferenciación de una referencia nula) y, en tiempo de ejecución, la llamada al método lanza una excepción [NullReferenceException]. Para que [p1] haga referencia a un objeto, hay que escribir:

    1
    Person p1 = new Person();

    Esto crea un objeto de tipo [Person] que aún no ha sido inicializado: sus campos tienen los valores predeterminados, en este caso la cadena vacía para [lastName] y [firstName], y 0 para [age] (un campo numérico sin valor inicial explícito vale 0; un campo de tipo referencia vale [null]). Ahora que [p1] hace referencia a un objeto, la instrucción de inicialización de ese objeto, [p1.Initialize("Jean", "Dupont", 30)], es válida.

    4.1.6. La palabra clave this

    Veamos el código del método [Initialize]:

    11
12
13
14
15
16
        public void Initialize(string p, string n, int age)
    {
        this.firstName = p;
        this.lastName = n;
        this.age = age;
    }

    La instrucción [this.firstName = p] significa que al campo [firstName] del objeto actual ([this]) se le asigna el valor [p]. La palabra clave [this] hace referencia al objeto actual, aquel sobre el cual se ejecuta el método. ¿Cómo lo sabemos? Veamos cómo se inicializa el objeto referenciado por [p1] en el programa que lo llama:

    1
    p1.Initialize("Jean", "Dupont", 30);

    Se llama al método [Initialize] del objeto [p1]. Cuando, dentro de este método, se hace referencia al objeto [this], en realidad se trata del objeto [p1]. El método [Initialize] también podría haberse escrito así:

    1
2
3
4
5
6
        public void Initialize(string p, string n, int age)
    {
        firstName = p;
        lastName = n;
        this.age = age;
    }

    Cuando un método de un objeto hace referencia a un campo [A] de ese objeto, se sobrentiende la notación [this.A]. Debe usarse explícitamente cuando hay un conflicto de identificadores. Es el caso de la instrucción [this.age = age;], donde [age] designa a la vez un campo del objeto actual y el parámetro [age] recibido por el método. En ese caso, la ambigüedad debe resolverse haciendo referencia al campo [age] como [this.age].

    4.1.8. Aplicaciones de un solo archivo

    Para un ejemplo corto, un proyecto resulta innecesariamente pesado. Desde la versión 10, .NET puede ejecutar directamente un archivo fuente independiente, sin un archivo [.csproj]: es una aplicación de un solo archivo, que utilizamos en el capítulo anterior. Las opciones del proyecto (tipos que admiten valores NULL habilitados, [using] implícitos) son las mismas que las de un proyecto de consola. Usaremos este formato siempre que el ejemplo contenga solo una o dos clases.

    El archivo contiene entonces las instrucciones de nivel superior seguidas de las declaraciones de clases: el compilador impone este orden, ya que las instrucciones de nivel superior deben preceder a cualquier declaración de tipo (clase, estructura, interfaz, etc.) en el archivo. Las clases declaradas de este modo no pertenecen a ningún espacio de nombres, lo cual es irrelevante en un programa de un solo archivo.

    4.1.10. Constructores de la clase Person

    Un constructor es un método que lleva el nombre de la clase y se llama cuando se crea el objeto. Generalmente se usa para inicializar el objeto. Es un método que puede aceptar parámetros pero no devuelve ningún valor. Su declaración no va precedida de ningún tipo (ni siquiera [void]).

    Si una clase [C] tiene un constructor que acepta n parámetros, la declaración e inicialización de un objeto de esta clase puede hacerse de la siguiente manera:

    1
    C obj = new C(arg1, arg2, ... argn);

    o

    1
2
3
    C obj;
...
obj = new C(arg1, arg2, ... argn);

    Cuando una clase [C] tiene uno o más constructores, debe usarse uno de ellos para crear un objeto de esa clase. Si una clase [C] no tiene constructores, tiene un constructor predeterminado, que es el constructor sin parámetros [public C()]. Los campos del objeto conservan entonces sus valores iniciales. Esto es lo que ocurrió en los programas anteriores, donde habíamos escrito [new Person()].

    4.1.17. Propiedades automáticas

    En muchos casos, los métodos [get] y [set] de una propiedad simplemente leen y escriben un campo privado sin ningún procesamiento adicional. En tales casos, puede usarse una propiedad automática declarada de la siguiente manera:

    1
    public Type Property { get; set; }

    El campo privado asociado a la propiedad no se declara; el compilador lo genera automáticamente y solo se puede acceder a él a través de su propiedad. Así, en lugar de escribir el campo [firstName] y la propiedad [FirstName] para el programa [classes-07.cs], se puede escribir:

    1
        public string FirstName { get; set; } = "";

    sin declarar el campo privado [firstName]. La expresión [= ""] que sigue a la propiedad es el valor inicial del campo oculto. La diferencia entre las dos propiedades es que la primera valida el nombre en [set], mientras que la segunda no realiza ninguna validación.

    ¿Usar la propiedad automática [FirstName] equivale a declarar un campo público [public string FirstName;]? Para el usuario de la clase, la sintaxis es la misma. Sin embargo, no se recomienda declarar un campo de una clase como público: viola el concepto de encapsulación del estado de un objeto, que debe ser privado y estar expuesto mediante métodos públicos. Con una propiedad automática, se pueden agregar verificaciones posteriormente en [set] sin cambiar el código de los usuarios de la clase.

    4.2. La herencia mediante un ejemplo

    4.2.1. Descripción general

    Aquí abordamos el concepto de herencia. El propósito de la herencia es “personalizar” una clase existente para que satisfaga nuestras necesidades. Supongamos que queremos crear una clase llamada [Teacher]: un docente es un tipo específico de persona. Tiene atributos que otras personas no tienen: la materia que enseña, por ejemplo. Pero también tiene los atributos comunes a todas las personas: nombre, apellido y edad. Un docente es, por lo tanto, un miembro de pleno derecho de la clase [Person] pero tiene atributos adicionales. En lugar de crear una clase [Teacher] desde cero, preferimos apoyarnos en la clase existente [Person] y adaptarla a las características específicas de los docentes. El concepto de herencia nos permite hacerlo.

    Para indicar que la clase [Teacher] hereda las propiedades de la clase [Person], escribimos:

    1
    public class Teacher : Person

    [Person] se denomina clase padre (o base), y [Teacher] se denomina clase derivada (o hija). Un objeto [Teacher] tiene todas las características de un objeto [Person]: tiene los mismos campos y métodos. Estos campos y métodos de la clase padre no se repiten en la definición de la clase hija; simplemente se especifican los campos y métodos que agrega la clase hija. Una clase de C# solo puede derivar de una única clase padre.

    • en la clase padre de su clase padre, si existe;

    4.2.4. Polimorfismo

    Consideremos una jerarquía de clases: C0 ← C1 ← C2 ← … ← Cn, donde Ci ← Cj indica que la clase Cj deriva de la clase Ci. Esto implica que la clase Cj tiene todas las características de la clase Ci más otras adicionales. Sean Oi objetos de tipo Ci. Es válido escribir [Oi = Oj] con j > i. En efecto, por herencia, la clase Cj tiene todas las características de la clase Ci más otras adicionales. Por lo tanto, un objeto Oj de tipo Cj contiene un objeto de tipo Ci. La operación [Oi = Oj] hace que Oi sea una referencia al objeto de tipo Ci contenido dentro del objeto Oj.

    El hecho de que una variable Oi de clase Ci pueda hacer referencia no solo a un objeto de clase Ci sino a cualquier objeto derivado de la clase Ci se denomina polimorfismo: la capacidad de una variable de hacer referencia a diferentes tipos de objetos.

    4.2.7. Clases selladas

    La clase [Teacher] del proyecto [Inheritance2] se declara como [public sealed class Teacher : Person]. La palabra clave [sealed] impide derivar clases de la clase [Teacher]: el compilador rechazaría la declaración [class TeacherResearcher : Teacher]. Una clase se sella cuando no está destinada a ser derivada; además, el compilador y el entorno de ejecución pueden optimizar las llamadas a sus métodos virtuales. La palabra clave también se aplica a un método o propiedad redefinido: [public sealed override string Identity] impediría que las clases derivadas lo redefinan nuevamente, sin prohibir la derivación de la clase.

    A la inversa, un método o propiedad que no está declarado como [virtual], [abstract] (véase más adelante) ni [override] no puede sobrescribirse con [override]: en C#, a diferencia de Java, los métodos no son virtuales de forma predeterminada.

    4.3. Redefinir el significado de un operador para una clase

    4.3.1. Introducción

    Consideremos la expresión [op1 + op2], donde [op1] y [op2] son dos operandos. Es posible redefinir el significado del operador [+]. Si el operando [op1] es una instancia de la clase [C1], debe definirse un método estático en la clase [C1] con la siguiente firma:

    1
    public static Type operator +(C1 operand1, C2 operand2)

    Cuando el compilador encuentra la expresión [op1 + op2], la traduce a [C1.operator +(op1, op2)]. El tipo devuelto por el método [operator] es importante. En efecto, consideremos la operación [op1 + op2 + op3]. El compilador la traduce como [(op1 + op2) + op3]. Sea [res12] el resultado de [op1 + op2]. La siguiente operación que se realiza es [res12 + op3]. Si [res12] es de tipo [C1], también se traducirá a [C1.operator +(res12, op3)]. Esto permite encadenar operaciones.

    También pueden redefinirse los operadores unarios, que tienen un solo operando. Así, si [op1] es un objeto de tipo [C1], la operación [op1++] puede redefinirse mediante un método estático de la clase [C1]:

    1
    public static C1 operator ++(C1 operand1)

    Lo que se ha expuesto aquí se aplica a la mayoría de los operadores, con algunas excepciones:

    • los operadores [==] y [!=] deben redefinirse juntos, al igual que [<] y [>], [<=] y [>=];
    • los operadores [&&], [||], [=], [.], [?:], [??] y [new] no pueden redefinirse;
    • hasta C# 13, los operadores de asignación compuesta ([+=], [-=], …) no podían sobrescribirse: [a += b] siempre se compilaba como [a = a + b]. C# 14 permite sobrescribirlos, como veremos.

    4.3.3. Operadores de asignación compuesta (C# 14)

    ¿Por qué definir el operador [+=] cuando [l = l + p] produce el mismo resultado? Si la clase no define [+=], el compilador traduce [l += p] a [l = l + p]: se crea una nueva lista, se copian en ella todas las personas de [l] y luego [l] pasa a hacer referencia a esta nueva lista, mientras que el recolector de basura descarta la anterior.     Por lo tanto, de estas explicaciones podemos concluir que:

    • el valor de una variable de tipo estructura es la estructura misma;
    • el valor de una variable de tipo clase es la dirección del objeto al que apunta.

    Se dice que las estructuras son tipos de valor y las clases son tipos de referencia. Los tipos simples de C# ([int], [double], [decimal], [bool], [char], …) son estructuras de .NET ([System.Int32], [System.Double], …), mientras que [string] y los arreglos son tipos de referencia. Una estructura es adecuada para representar un dato pequeño (un punto, un color, una fecha, un monto…) que se trata como un valor. Una estructura no se asigna individualmente en el montón del recolector de basura: una variable local de tipo estructura se coloca generalmente en la pila, y un arreglo de estructuras contiene las estructuras mismas y no referencias a ellas.

            return average.Value;

    {

        return standardDeviation.Value;

    private double ComputeAverage()
    {
        if (Grades.Count == 0)
        {
            return -1;
        }
        double sum = 0;
        foreach (Grade grade in Grades)
        {
            sum += grade.Value;
        }
        return sum / Grades.Count;
    }

    private double ComputeStandardDeviation()
    {
        if (Grades.Count == 0)
        {
            return -1;
        }
        double m = Average;
        double squares = 0;
        foreach (Grade grade in Grades)
        {
            squares += Math.Pow(grade.Value - m, 2);
        }
        return Math.Sqrt(squares / Grades.Count);
    }

    {
        return $"subject={Subject}, grades=({string.Join(",", Grades)})";

    public T Pop()

    Significado
    [where T : struct]

    [where T : IInterface]

    [where T : U]
    T debe ser el tipo U o un tipo derivado de U, donde U es otro parámetro genérico

    4.8.3. Una interfaz genérica: IComparer<T>

    Para ilustrar el concepto de interfaz genérica, ordenaremos un arreglo de personas primero por sus nombres y luego por sus edades. El método que permite ordenar un arreglo es el método estático [Sort] de la clase [Array]. Tiene distintas firmas (está sobrecargado). Usaremos la siguiente firma:

    1
    public static void Sort<T>(T[] array, IComparer<T>? comparer)

    [Sort] es un método genérico donde [T] designa cualquier tipo. El método recibe dos parámetros:

    • [T[] array]: el arreglo de elementos de tipo [T] que se va a ordenar;
    • [IComparer<T>? comparer]: una referencia a un objeto que implementa la interfaz [IComparer<T>].

    [IComparer<T>] es una interfaz genérica definida de la siguiente manera (definición simplificada):

    1
2
3
4
    public interface IComparer<in T>
{
    int Compare(T? x, T? y);
}

    La interfaz [IComparer<T>] tiene un solo método. El método [Compare]:

    • recibe dos parámetros, [x] y [y], de tipo [T]. El tipo [T?] indica que sus valores pueden ser [null] (la palabra clave [in] es un detalle técnico que no explicaremos aquí);
    • devuelve un número positivo si x > y, 0 si x == y y un número negativo si x < y. Corresponde al desarrollador definir el significado de los operadores <, == y >. Por ejemplo, si [p1] y [p2] son dos objetos [Person], podemos decir que p1 > p2 si el nombre de [p1] va después del nombre de [p2] en orden alfabético. Esto dará como resultado un orden ascendente según los nombres de las personas. Si queremos ordenar por edad, diremos que p1 > p2 si la edad de [p1] es mayor que la edad de [p2];
    • para ordenar de forma descendente, basta con invertir el signo de los resultados.

    {
        // descartamos el caso de las referencias nulas

    4.9. Espacios de nombres

    Para escribir una línea en la pantalla, usamos la instrucción [Console.WriteLine(...)]. Si consultamos la definición de la clase [Console] en la documentación de .NET, vemos que forma parte del espacio de nombres [System]. Esto significa que la clase [Console] debería designarse como [System.Console], y que en realidad deberíamos escribir [System.Console.WriteLine(...)]. Evitamos esto mediante una cláusula [using]:

    1
2
3
    using System;
...
Console.WriteLine(...);

    Esto significa que el espacio de nombres [System] se importa mediante la cláusula [using]. Cuando el compilador encuentra un nombre de clase (en este caso, [Console]), lo busca en los diversos espacios de nombres importados por las cláusulas [using]. Aquí encuentra la clase [Console] en el espacio de nombres [System]. En un proyecto .NET reciente, ni siquiera necesitamos escribir [using System;]: este espacio de nombres está incluido en las instrucciones implícitas **using** del proyecto, como vimos al comienzo del capítulo.

    La documentación proporciona un segundo dato sobre la clase [Console]: el ensamblado que la contiene, el archivo [System.Console.dll]. Un ensamblado es el resultado de compilar un proyecto: un archivo [.dll] (biblioteca) o un ejecutable. Para usar las clases de un ensamblado, el compilador debe conocerlo. El curso de 2008 mostraba cómo pasar estas referencias al compilador [csc] por la línea de comandos ([csc /r:fic1.dll /r:fic2.dll prog.cs]). Hoy ya no invocamos el compilador directamente: los ensamblados del framework .NET se referencian automáticamente, y el archivo [.csproj] referencia las demás bibliotecas, ya sea como paquetes ([PackageReference]) o como proyectos ([ProjectReference]), como veremos en el capítulo 6, dedicado a las arquitecturas en capas.

    Al crear una clase, se puede crear dentro de un espacio de nombres. La finalidad de estos espacios de nombres es evitar conflictos de nombres entre clases, por ejemplo, cuando se distribuyen. Consideremos dos empresas, E1 y E2, que distribuyen clases empaquetadas en los ensamblados [e1.dll] y [e2.dll], respectivamente. Supongamos que un cliente C compra ambos conjuntos de clases, en los que las dos empresas han definido una clase llamada [Person]. Si el programa del cliente usa la clase [Person], el compilador no sabrá si debe usar la clase [Person] de [e1.dll] o la de [e2.dll]. Informará de un error. Si la empresa E1 crea sus clases en un espacio de nombres llamado [E1] y la empresa E2 crea las suyas en un espacio de nombres llamado [E2], las dos clases llamadas [Person] pasarán a llamarse [E1.Person] y [E2.Person]. El cliente deberá usar [E1.Person] o [E2.Person] (o un alias) en sus clases, pero no [Person]. El espacio de nombres resuelve esta ambigüedad.

    Para crear una clase en un espacio de nombres, el curso de 2008 indicaba:

    4.14. Tipos de referencia que admiten valores nulos

    Desde el comienzo de este capítulo, nuestros proyectos tienen habilitados los tipos de referencia que admiten valores nulos ([<Nullable>enable</Nullable>] en el archivo [.csproj], una opción habilitada de manera predeterminada en las aplicaciones de un solo archivo). El principio es el siguiente:

    • una variable, campo, parámetro o resultado de tipo de referencia declarado sin signo de interrogación (por ejemplo, de tipo [Person]) nunca debería ser igual a [null];
    • si puede ser [null], se declara con un signo de interrogación: [Person?];
    • el compilador analiza el flujo del programa y emite una advertencia cada vez que se usa un valor potencialmente nulo sin verificación, o se asigna a una variable que no admite valores nulos.

    El lenguaje no prohíbe nada en tiempo de ejecución: se trata de advertencias de compilación, pero un programa que compila sin advertencias es mucho menos propenso a la excepción [NullReferenceException], el error de ejecución más común.     Retomaremos el cálculo del impuesto que vimos en el capítulo anterior (versión 1) y lo implementaremos con clases e interfaces. Recordemos el problema. Queremos escribir un programa para calcular el impuesto de un contribuyente. Consideraremos el caso simplificado de un contribuyente que solo tiene un salario que declarar (con la tabla de 2004 para los ingresos de 2003, conservada tal cual: es un ejercicio):

// un tramo de la tabla de impuestos

    El curso de 2008 usaba una estructura con tres propiedades automáticas de lectura y escritura. Nosotros usamos una estructura record inmutable ([readonly record struct]):

    • una estructura porque un tramo es un dato pequeño sin identidad, definido únicamente por su valor: un arreglo de tramos contiene directamente los tramos, sin un objeto separado en memoria para cada uno. Con tres [decimal] (48 bytes), la estructura supera el tamaño de aproximadamente 16 bytes que suele recomendarse para una estructura; esto no es un problema aquí: hay pocos tramos y solo se copian cuando se leen;
    • inmutable ([readonly]) porque no hay razón para que un tramo impositivo se modifique una vez creado. El curso de 2008, dicho sea de paso, modificaba el límite del último tramo durante el cálculo, un efecto secundario que eliminamos;
    • un record ([record]) porque el compilador genera el constructor, las propiedades, [ToString], y el operador de igualdad a partir de una sola línea.

    namespace TaxV2;

public abstract class AbstractTax : ITax
{
    // los tramos del impuesto necesarios para el cálculo provienen de una fuente externa
    // que solo las clases derivadas conocen
    protected abstract TaxBracket[] TaxBrackets { get; }

    // cálculo del impuesto
    public int Calculate(bool married, int nbChildren, int salary)
    {
        // cálculo del número de partes
        decimal shares = (decimal)nbChildren / 2 + (married ? 2 : 1);
        if (nbChildren >= 3)
        {
            shares += 0.5m;
        }
        // cálculo del ingreso gravable y del cociente familiar
        decimal income = 0.72m * salary;
        decimal quotient = income / shares;
        // búsqueda del tramo del impuesto: se usa el último si ningún límite se ajusta
        TaxBracket[] brackets = TaxBrackets;
        TaxBracket bracket = brackets[^1];
        for (int i = 0; i < brackets.Length - 1; i++)
        {
            if (quotient <= brackets[i].Limit)
            {
                bracket = brackets[i];
                break;
            }
        }
        // cálculo del impuesto
        return (int)(income * bracket.CoeffR - shares * bracket.CoeffN);
    }
}
    • Línea 3: la clase [AbstractTax] implementa la interfaz [ITax];
    • línea 7: los datos de la tabla, en forma de una propiedad abstracta protegida. La clase [AbstractTax] no sabe de dónde provienen estos datos (escritos en el código, leídos de un archivo, de una base de datos, etc.). Eso lo deja en manos de las clases derivadas. Por eso se declara abstracta, lo que impide instanciarla. El curso de 2008 usaba un campo protegido que las clases derivadas debían inicializar; la propiedad abstracta obliga a las clases derivadas a proporcionarla: el compilador lo verifica;
    • líneas 10–33: la implementación del método [Calculate] de la interfaz [ITax]. Las clases derivadas no tendrán que reescribir este método. La clase [AbstractTax] sirve así como clase de factorización para las clases derivadas: contiene lo que es común a todas ellas;
    • línea 13: el número de partes. La conversión [(decimal)nbChildren] es esencial: sin ella, [nbChildren / 2] sería una división entera (3 / 2 = 1). La expresión [married ? 2 : 1] es igual a 2 para un contribuyente casado y a 1 en caso contrario;
    • Líneas 19–20: el ingreso imponible y el cociente familiar. Todos los cálculos se realizan con [decimal], un tipo adecuado para los importes: el sufijo [m] de [0.72m] denota una constante de este tipo;
    • líneas 22–29: determinación del tramo impositivo. Por defecto, es el último tramo ([brackets[^1]], línea 23). El bucle recorre todos los tramos excepto el último y se detiene ([break]) en el primer tramo cuyo límite es mayor o igual que el cociente familiar;
    • línea 33: cálculo del impuesto. La conversión [(int)] trunca el resultado [decimal] a su parte entera.

public class HardwiredTax : AbstractTax

    private static readonly decimal[] limits = [4962m, 8382m, 14753m, 23888m, 38868m, 47932m, 0m];
    private static readonly decimal[] coeffR = [0m, 0.068m, 0.191m, 0.283m, 0.374m, 0.426m, 0.481m];

        taxBrackets = new TaxBracket[limits.Length];

}

const string syntax = """
    syntax: Married NbChildren Salary
    Married: y for married, n for not married
    NbChildren: number of children
    Salary: annual salary in euros
    """;

// creación de un objeto ITax
ITax tax = new HardwiredTax();

// bucle de entrada
while (true)
{
    // se piden los parámetros del cálculo del impuesto
    Console.Write("Tax calculation parameters in the format: Married (y/n) NbChildren Salary, or nothing to stop: ");
    string parameters = (Console.ReadLine() ?? "").Trim();
    // ¿algo que hacer?
    if (parameters == "")
    {
        break;
    }
    // verificación del número de campos de la línea escrita
    string[] fields = parameters.Split(' ', StringSplitOptions.RemoveEmptyEntries);
    if (fields.Length != 3)
    {
        Console.WriteLine(syntax);
        continue;
    }
    // verificación de la validez de los parámetros
    // married
    string married = fields[0].ToLower();
    if (married != "y" && married != "n")
    {
        Console.WriteLine(syntax + "\nIncorrect married argument: type y or n");
        continue;
    }
    // nbChildren
    if (!int.TryParse(fields[1], out int nbChildren) || nbChildren < 0)
    {
        Console.WriteLine(syntax + "\nIncorrect NbChildren argument: type a positive or zero integer");
        continue;
    }
    // salary
    if (!int.TryParse(fields[2], out int salary) || salary < 0)
    {
        Console.WriteLine(syntax + "\nIncorrect salary argument: type a positive or zero integer");
        continue;
    }
    // los parámetros son correctos: calculamos el impuesto
    Console.WriteLine($"Tax={tax.Calculate(married == "y", nbChildren, salary)} euros");
}
