    8. Hilos de ejecución

    Este capítulo presenta la ejecución simultánea de varios fragmentos de código dentro de un mismo programa: los hilos (hilos de ejecución) y las herramientas que sirven para sincronizarlos. En 2008, la mayoría de las máquinas tenían un solo procesador, y el paralelismo era en gran medida una ilusión mantenida por el sistema operativo. Hoy en día, incluso la computadora portátil más básica tiene varios núcleos: varios hilos se ejecutan realmente al mismo tiempo, lo que hace aún más frecuentes los problemas de sincronización que se tratan aquí.

    Los ejemplos son aplicaciones de un solo archivo ([dotnet run threads-01.cs]) ubicadas en la carpeta [08-threads]. Tenga en cuenta que las directivas [using] implícitas de estas aplicaciones incluyen [System.Threading] y [System.Threading.Tasks]: las clases [Thread], [Lock], [Mutex], [Monitor], [Interlocked], [Task]… pueden utilizarse sin la directiva [using].

    Una advertencia antes de comenzar: los resultados de un programa multihilo varían de una ejecución a otra. El orden en que se asigna el procesador a los hilos depende del sistema operativo, del número de procesadores y de la carga de la máquina. Los resultados mostrados en este capítulo se obtuvieron en una máquina Linux de dos procesadores compartida con otros programas. Si usted ejecuta los ejemplos, obtendrá resultados similares, pero rara vez idénticos.

    8.1. La clase Thread

    Cuando se inicia una aplicación, se ejecuta en un flujo de ejecución llamado hilo. La clase de .NET que modela un hilo es la clase [System.Threading.Thread]. Sus principales constructores, propiedades y métodos son los siguientes:

    Miembro
    Función
    [Thread(ThreadStart start)]
    crea un hilo que ejecutará el método [start]. El delegado [ThreadStart] hace referencia a un método sin parámetros y sin valor de retorno: [void M()]
    [Thread(ParameterizedThreadStart start)]
    igual que el anterior, pero con un método que tiene un parámetro de tipo [object?]: [void M(object? obj)]
    [static Thread CurrentThread]
    el hilo que ejecuta el código que solicitó esta propiedad
    [string? Name]
    el nombre del hilo, útil para el seguimiento
    [int ManagedThreadId]
    un identificador numérico único del hilo
    [bool IsBackground]
    indica si el hilo es un hilo en segundo plano (véase más adelante)
    [bool IsAlive]
    indica si el hilo se está ejecutando actualmente
    [void Start()], [void Start(object? obj)]
    inicia la ejecución del hilo, pasándole opcionalmente información de tipo [object]
    [void Join()], [bool Join(TimeSpan timeout)]
    El hilo T1, que ejecuta [T2.Join()], se bloquea hasta que el hilo T2 haya terminado. La segunda forma limita la duración de la espera
    [static void Sleep(int ms)]

    El curso de 2008 también trataba el método [Abort], que terminaba forzosamente un hilo. En la práctica ya no existe: desde .NET Core, lanza la excepción [PlatformNotSupportedException]. Detener bruscamente un hilo podía dejar los datos que manejaba en un estado inconsistente. Hoy en día, se le pide a un hilo que se detenga de manera cooperativa, mediante un token de cancelación ([CancellationToken]) que el hilo verifica regularmente: lo veremos en el próximo capítulo.

    8.2. Creación de hilos de ejecución

    Es posible tener aplicaciones en las que fragmentos de código se ejecutan "simultáneamente" en distintos hilos de ejecución. Si la máquina tiene menos procesadores que hilos listos para ejecutarse, los hilos comparten los procesadores: cada uno utiliza un procesador por turnos durante un breve lapso (unos pocos milisegundos). En una máquina multiprocesador, varios hilos se ejecutan realmente al mismo tiempo. El tiempo asignado a un hilo depende de varios factores, entre ellos su prioridad, que tiene un valor predeterminado pero puede establecerse por programa (propiedad [Priority]). Un hilo que tiene el procesador puede liberarlo antes de tiempo:

    • al esperar un evento (la finalización de otro hilo con [Join], la espera de una señal);
    • al entrar en estado de suspensión durante un tiempo determinado ([Sleep]).

    Primero se crea un hilo T con uno de los constructores presentados anteriormente, por ejemplo:

    1
    Thread t = new Thread(Display);

    donde [Display] es un método con una de las dos firmas siguientes:

    1
2
    void Display();
void Display(object? obj);

    Crear un hilo no lo inicia:

    • la ejecución del hilo T se inicia con [T.Start()]: el método pasado al constructor de T es entonces ejecutado por el hilo T. El código que ejecuta la instrucción [T.Start()] no espera a que el hilo T termine; pasa inmediatamente a la siguiente instrucción. Tenemos entonces dos hilos en ejecución paralela. A menudo necesitan comunicarse entre sí para seguir el avance del trabajo compartido: este es el problema de la sincronización de hilos;
    • Una vez iniciado, el hilo T se ejecuta de forma autónoma. Se detiene cuando el método que ejecuta termina;
    • podemos esperar a que termine de ejecutarse mediante [T.Join()]. Esta es una instrucción bloqueante: el hilo que la ejecuta se bloquea hasta que el hilo T haya terminado su trabajo. Es un método básico de sincronización.

    // creación de hilos de ejecución

// damos nombre al hilo principal
Thread.CurrentThread.Name = "Main";

// creación de 5 hilos
var tasks = new Thread[5];
for (int i = 0; i < tasks.Length; i++)
{
    // el hilo n.º i ejecutará el método Display
    tasks[i] = new Thread(Display);
    // le damos un nombre
    tasks[i].Name = i.ToString();
    // iniciamos su ejecución (operación no bloqueante)
    tasks[i].Start();
}

// fin del hilo principal
Console.WriteLine($"End of thread {Thread.CurrentThread.Name} at {DateTime.Now:HH:mm:ss.fff}");

// el método ejecutado por los hilos
static void Display()
{
    // el hilo que ejecuta el método
    Thread current = Thread.CurrentThread;
    Console.WriteLine($"Start of execution of the Display method in thread {current.Name} (id {current.ManagedThreadId}): {DateTime.Now:HH:mm:ss.fff}");
    // pausa de 1 s
    Thread.Sleep(1000);
    Console.WriteLine($"End of execution of the Display method in thread {current.Name}: {DateTime.Now:HH:mm:ss.fff}");
}

    • línea 19: el hilo principal llega al final del programa;

    • línea 28: todo hilo que ejecuta el método [Display] hace una pausa de 1 segundo. El procesador se cede entonces a otro hilo que espera el procesador. Al final de la pausa de 1 segundo, el hilo en pausa vuelve a ser elegible para obtener el procesador. Lo obtendrá cuando le llegue su turno.

    Estos resultados son muy instructivos:

    • En primer lugar, vemos que lanzar un hilo no es bloqueante. El hilo principal lanzó 5 hilos y llegó al final del programa (línea 4) aunque tres de los hilos lanzados aún no habían mostrado su primer mensaje;
    • el orden en que se ejecutan los hilos es impredecible: en esta ejecución, los hilos 2 y 4 mostraron sus mensajes de inicio antes que el hilo 0. Aquí el sistema operativo tiene 6 hilos y 2 procesadores; asigna los procesadores a estos hilos según sus propias reglas;
    • También observamos que el orden de las impresiones no siempre sigue el orden de las horas mostradas: la hora se calcula antes de mostrarse, y mientras tanto otro hilo puede haber escrito en la consola. [Console.WriteLine] es seguro para hilos (thread-safe): dos líneas escritas por dos hilos no se mezclan, pero su orden no está garantizado;
    • cada hilo hace una pausa de un segundo con [Sleep] y luego termina de ejecutar el método [Display];
    • Por último, el programa no se detuvo cuando el hilo principal terminó su trabajo: el proceso esperó a que los 5 hilos terminaran. Esto se debe a que estos hilos son hilos en primer plano: un proceso de .NET termina cuando todos sus hilos en primer plano han terminado.

    // espera del fin de un hilo con Join - hilos creados con una lambda

// damos nombre al hilo principal
Thread.CurrentThread.Name = "Main";

// creación de 5 hilos
var tasks = new Thread[5];
for (int i = 0; i < tasks.Length; i++)
{
    // copia local de i, capturada por la lambda
    int number = i;
    // el hilo ejecuta la lambda, que llama a Display con un parámetro con tipo
    tasks[i] = new Thread(() => Display(number, 1000 + 100 * number)) { Name = i.ToString() };
    tasks[i].Start();
}

// esperamos el fin de todos los hilos
foreach (Thread task in tasks)
{
    // el hilo principal queda bloqueado hasta el fin del hilo [task]
    task.Join();
}
// fin del hilo principal
Console.WriteLine($"End of thread {Thread.CurrentThread.Name} at {DateTime.Now:HH:mm:ss.fff}");

// el método ejecutado por los hilos
static void Display(int number, int duration)
{
    Console.WriteLine($"Start of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
    // pausa de [duration] milisegundos
    Thread.Sleep(duration);
    Console.WriteLine($"End of execution of task {number} in thread {Thread.CurrentThread.Name}: {DateTime.Now:HH:mm:ss.fff}");
}

    • Línea 13: el hilo ejecuta la lambda [() => Display(number, 1000 + 100 * number)]. Una lambda sin parámetros y sin valor de retorno es compatible con el delegado [ThreadStart]. Esta sintaxis permite llamar a un método con parámetros tipados (en este caso, dos [int]) en lugar de la firma impuesta [void M(object? obj)];
    • Línea 11: la lambda utiliza una copia de la variable de bucle [i]. Esto es esencial: una lambda captura la variable, no su valor. En un bucle [for], la variable [i] es única para todas las iteraciones; si la lambda utilizara [i], un hilo que arranque tarde podría leer el valor de [i] de una iteración posterior, o incluso el valor final 5. En cambio, la variable [number], declarada dentro del cuerpo del bucle, es una variable nueva en cada iteración (la variable de un bucle [foreach] también es nueva en cada iteración, a partir de C# 5);
    • líneas 18–21: el hilo principal espera a cada uno de los hilos. Primero se bloquea esperando al hilo 0, luego al hilo 1, y así sucesivamente. Al salir del bucle, los 5 hilos que lanzó han terminado;
    • línea 31: la tarea n.º i duerme 1000 + 100 × i milisegundos, de modo que los hilos terminen en un orden conocido.

    8.3. Las ventajas de los hilos

    Ahora que hemos puesto de relieve la existencia de un hilo predeterminado (el que ejecuta el programa principal) y sabemos cómo crear hilos adicionales, veamos las ventajas de los hilos. Tienen dos usos principales:

    • aprovechar todos los procesadores de la máquina para un cálculo que consume mucho tiempo: el trabajo se divide en fragmentos asignados a distintos hilos. Lo haremos con la biblioteca [Parallel] al final de este capítulo;
    • realizar varias tareas simultáneamente, en particular cuando algunas de ellas consisten principalmente en esperar (una respuesta de la red, una lectura de disco o una entrada del usuario). Es el caso de las aplicaciones de Internet cliente/servidor, que trataremos en un capítulo posterior.

Si tomamos el ejemplo de un servidor de archivos, sabemos que una transferencia a veces puede durar varios minutos.     8.5. Acceso concurrente a recursos compartidos

    8.5.1. Acceso concurrente no sincronizado

    En el apartado anterior, la información se intercambiaba solo entre dos hilos y en momentos muy precisos: era un ejemplo clásico de paso de parámetros. Hay otros casos en los que la información es compartida por varios hilos que pueden querer leerla o actualizarla al mismo tiempo. Esto plantea el problema de la integridad de esa información. Supongamos que la información compartida es una estructura S que contiene diversos datos I1, I2, ..., In:

    • un hilo T1 comienza a actualizar la estructura S: modifica el campo I1 y es interrumpido antes de completar la actualización de la estructura S;
    • un hilo T2 que obtiene el procesador lee entonces la estructura S para tomar decisiones. Lee una estructura en un estado inestable: algunos campos están actualizados y otros no.

    • el recurso compartido es un contador que debe ser incrementado por cada hilo generado;
    • al final de la aplicación, se muestra el valor del contador. Por lo tanto, debería ser igual a n.

    8.5.3. La clase Mutex

    La clase [System.Threading.Mutex] también permite delimitar secciones críticas. Se diferencia de la cláusula [lock] en cuanto a su visibilidad:

    • la cláusula [lock] sincroniza hilos dentro de la misma aplicación;
    • la clase [Mutex] puede sincronizar hilos de distintas aplicaciones (o procesos) si se le asigna un nombre.

    Un [Mutex] es un objeto del sistema operativo: su uso consume muchos más recursos que el de un [lock]. Para hilos del mismo proceso, preferimos por lo tanto utilizar [lock]; [Mutex] se utiliza principalmente entre procesos. Utilizaremos los siguientes constructores y métodos:

    Miembro
    Función
    [Mutex()]
    crea un Mutex M anónimo, utilizable por los hilos del proceso
    [Mutex(bool initiallyOwned, string name)]
    crea o abre el mutex con nombre [name], compartido por todos los procesos que usan este nombre
    [bool WaitOne()]
    El hilo T1, que ejecuta [M.WaitOne()], solicita la propiedad del mutex M. Si M no está en poder de ningún hilo, se le concede a T1. Si un hilo T2 intenta entonces la misma operación, se bloquea: un mutex solo puede pertenecer a un hilo. T2 se desbloqueará cuando T1 libere M. Así, varios hilos pueden quedar bloqueados a la espera de M
    [bool WaitOne(TimeSpan timeout)]
    Igual que el anterior, pero la espera se limita a [timeout]. El método devuelve [false] si no se pudo adquirir el mutex

    8.5.4. La clase AutoResetEvent

    Un objeto [AutoResetEvent] es una barrera que deja pasar un solo hilo a la vez. Se construye de la siguiente manera:

    1
    AutoResetEvent barrier = new AutoResetEvent(state);

    El booleano [state] indica si la barrera está cerrada ([false]) o abierta ([true]). Un hilo que desea atravesar la barrera lo indica de la siguiente manera:

    1
    barrier.WaitOne();
    • Si la barrera está abierta, el hilo pasa y la barrera se cierra automáticamente tras él (de ahí el nombre de la clase). Si varios hilos esperan, solo uno pasa;

    1
    barrier.Set();

    Un hilo también puede cerrar una barrera con [barrier.Reset()]. A diferencia de un mutex, una barrera no pertenece a ningún hilo en particular: cualquier hilo puede abrirla.     8.5.6. La clase Interlocked

    La clase [Interlocked] hace que operaciones simples sobre una variable sean atómicas: la operación la ejecuta el hilo por completo, sin que ningún otro hilo pueda observar o modificar la variable a mitad de la operación. Las herramientas anteriores ([lock], [Mutex], [AutoResetEvent]) están todas diseñadas para hacer atómico un grupo de operaciones, al costo de bloquear a otros hilos. Para operaciones simples pero frecuentes, la clase [Interlocked] evita este bloqueo mediante instrucciones especiales del procesador. Sus principales métodos estáticos son los siguientes:

    Método
    Función
    [int Increment(ref int x)]
    incrementa [x] en 1 y devuelve el nuevo valor
    [int Decrement(ref int x)]
    decrementa [x] en 1 y devuelve el nuevo valor
    [int Add(ref int x, int value)]
    suma [value] a [x] y devuelve el nuevo valor
    [int Exchange(ref int x, int value)]
    asigna [value] a [x] y devuelve el valor anterior
    [int CompareExchange(ref int x, int value, int comparand)]
    asigna [value] a [x] solo si [x] es igual a [comparand]; devuelve el valor anterior de [x]
    [long Read(ref long x)]
    lee atómicamente un valor de 64 bits (útil en un procesador de 32 bits)

    Estos métodos están disponibles para los tipos [int], [long], [uint], [ulong]y, en el caso de [Exchange] y [CompareExchange], para otros tipos. Los métodos [And] y [Or] (.NET 5) realizan atómicamente una operación "y" u "o" bit a bit.     8.6. Acceso concurrente a varios recursos compartidos

    8.6.1. Interbloqueo (deadlock)

    En nuestros ejemplos anteriores, se compartía un único recurso entre los distintos hilos. La situación se complica si hay varios recursos y dependen unos de otros. En particular, puede producirse un interbloqueo (deadlock): dos hilos se esperan mutuamente. Consideremos las siguientes acciones, que ocurren secuencialmente:

    • un hilo T1 adquiere el cerrojo V1 para acceder a un recurso compartido R1;
    • un hilo T2 adquiere el cerrojo V2 para acceder a un recurso compartido R2;
    • el hilo T1 solicita el cerrojo V2. Se bloquea;
    • el hilo T2 solicita el cerrojo V1. Se bloquea.

    Los hilos T1 y T2 se esperan mutuamente de manera indefinida. Son posibles varias soluciones:

    • solicitar ambos recursos al mismo tiempo mediante un único cerrojo. Esto no siempre es posible si implica un bloqueo prolongado de un recurso costoso;
    • adquirir siempre los cerrojos en el mismo orden: si todos los hilos adquieren V1 antes que V2, el interbloqueo es imposible. Esta es la regla más utilizada;
    • un hilo que tiene V1 y no puede adquirir V2 libera V1 para evitar el interbloqueo.

static void Work(Lock first, string firstName, Lock second, string secondName, TimeSpan timeout)

    {

        // damos tiempo al otro hilo para que tome su primer recurso

}

    8.6.2. Un ejemplo: lectores y escritores

    Consideremos el siguiente ejemplo:

    • tenemos un arreglo en el que algunos hilos escriben datos (los escritores) y otros los leen (los lectores);
    • los escritores son iguales entre sí pero exclusivos: solo un escritor a la vez puede depositar datos en el arreglo;
    • los lectores son iguales entre sí pero exclusivos: solo un lector a la vez puede leer los datos almacenados en el arreglo;
    • un lector solo puede leer datos del arreglo cuando un escritor ha colocado algunos allí, y un escritor solo puede colocar nuevos datos en el arreglo cuando los datos que ya están allí han sido leídos por un lector.

    Hay dos tipos de recursos compartidos:

    • el arreglo en el que se escribe: solo un escritor a la vez puede acceder a él;
    • el arreglo que se lee: solo un lector a la vez puede acceder a él.

    y un orden de utilización de estos recursos:

    • un lector debe siempre seguir a un escritor;
    • un escritor debe siempre seguir a un lector, excepto la primera vez.

    El acceso a estos dos recursos puede controlarse mediante dos barreras de tipo [AutoResetEvent]:

    • la barrera [canWrite] controla el acceso de los escritores al arreglo;
    • la barrera [canRead] controla el acceso de los lectores al arreglo;
    • la barrera [canWrite] se crea abierta, lo que permite pasar al primer escritor y bloquea a todos los demás;
    • La barrera [canRead] se crea en estado cerrado, bloqueando a todos los lectores;
    • cuando un escritor termina su trabajo, abre la barrera [canRead] para dejar pasar a un lector;
    • cuando un lector termina su trabajo, abre la barrera [canWrite] para dejar pasar a un escritor.

    8.6.3. La clase Monitor

    En el ejemplo anterior, cuando los escritores están bloqueados en la instrucción [canWrite.WaitOne()], uno de ellos —cualquiera— se desbloquea mediante la operación [canWrite.Set()]. Si se desea abrir la barrera para un escritor específico, las cosas se complican.

    Consideremos la analogía de una oficina de atención al público con ventanillas. Cuando llega un cliente, toma un número del dispensador y luego va a sentarse. Los clientes son llamados por su número mediante un altavoz. Mientras espera, el cliente puede hacer lo que quiera: leer o dormitar. Se despierta cada vez que el altavoz anuncia un número. Si es su número, el cliente se levanta y va a la ventanilla; de lo contrario, vuelve a lo que estaba haciendo. Podemos operar de manera similar con los hilos. Tomemos el ejemplo de los escritores:

    En la ventanilla
    Con hilos
    varios escritores esperan la misma ventanilla
    sus hilos están bloqueados
    la ventanilla queda disponible y se llama el número del siguiente escritor
    el hilo que leía el arreglo notifica a los escritores que el arreglo está disponible. Ese hilo u otro ha determinado qué escritor debe continuar
    Cada escritor verifica su número; solo el que tiene el número llamado pasa a la ventanilla; los demás vuelven a la cola de espera
    Cada hilo verifica si es el seleccionado. Si lo es, atraviesa la barrera; de lo contrario, vuelve a la cola de espera

    La clase [Monitor] implementa este escenario. Sus métodos estáticos son los siguientes:

    Método
    Función
    [Enter(object token)]
    Solicita el token: el hilo lo obtiene si está libre; de lo contrario, se bloquea hasta que quede libre
    [bool TryEnter(object token, TimeSpan timeout)]
    Igual que el anterior, con un tiempo de espera máximo
    [Exit(object token)]
    devuelve el token
    [bool Wait(object token)]
    devuelve el token y bloquea el hilo hasta que otro hilo señale un cambio mediante [Pulse] o [PulseAll]; el hilo debe entonces recuperar el token antes de continuar
    [Pulse(object token)]
    despierta a uno de los hilos bloqueados por [Wait] en este token
    [PulseAll(object token)]
    despierta a todos los hilos bloqueados por [Wait] en este token

    Los hilos que comparten un recurso (la ventanilla) acceden a él mediante un objeto que llamaremos token. Para atravesar la barrera que conduce a la ventanilla se necesita tener el token, y solo hay uno. Por lo tanto, los hilos deben pasarse el token entre sí:

    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Read] started by thread {name}");
        // solicitamos el token del contador de lectura
        lock (canRead)
        {
            // mientras no sea nuestro turno, devolvemos el token y esperamos
            while (!readingAllowed || ReadOrder[nextReader] != name)
            {
                Monitor.Wait(canRead);
            }
            // en el contador: lectura del arreglo
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: reader {name} read the number {data[i]}");
            }
            // siguiente lector
            readingAllowed = false;
            nextReader++;
            // notificamos a los escritores que pueden escribir
            lock (canWrite)
            {
                writingAllowed = true;
                Monitor.PulseAll(canWrite);
            }
            Console.WriteLine($"Method [Read] finished by thread {name}");
        }
    }

    // escritura en el arreglo
    public static void Write()
    {
        string name = Thread.CurrentThread.Name ?? "?";
        Console.WriteLine($"Method [Write] started by thread {name}");
        // solicitamos el token del contador de escritura
        lock (canWrite)
        {
            // mientras no sea nuestro turno, devolvemos el token y esperamos
            while (!writingAllowed || WriteOrder[nextWriter] != name)
            {
                Monitor.Wait(canWrite);
            }
            // en el contador: escritura del arreglo
            for (int i = 0; i < data.Length; i++)
            {
                Thread.Sleep(500);
                data[i] = Random.Shared.Next(0, 1000);
                Console.WriteLine($"{DateTime.Now:HH:mm:ss.fff}: writer {name} wrote the number {data[i]}");
            }
            // siguiente escritor
            writingAllowed = false;
            nextWriter++;
            // notificamos a los lectores que pueden leer
            lock (canRead)
            {
                readingAllowed = true;
                Monitor.PulseAll(canRead);
            }
            Console.WriteLine($"Method [Write] finished by thread {name}");
        }
    }
}

    • línea 39: el booleano [readingAllowed];

    • línea 41: [nextReader] es el índice en este arreglo del siguiente lector autorizado a pasar a la ventanilla.

    El programa principal:

    • líneas 7–9: los lectores pasarán a la ventanilla en orden inverso al de su creación (R2, R1, R0), y los escritores en el orden en que fueron creados (W0, W1, W2). Los arreglos se construyen mediante una expresión de colección [.. sequence], que crea un arreglo a partir de una consulta LINQ;
    • líneas 18–22: creación e inicialización de los lectores, seguidos de los escritores. Todos quedarán bloqueados, ya que no se permite ni leer ni escribir;
    • línea 26: se habilita la escritura y se notifica a los escritores que algo ha cambiado (método [AllowWriting], líneas 48–54).

    El método [Read]:

    • líneas 64–86: todo el proceso en la ventanilla de lectura está controlado por [lock] sobre el token [canRead]. El lector que lo obtiene lo conserva durante todo su paso por la ventanilla;
    • líneas 67–69: un lector que ha adquirido el token lo devuelve si la lectura no está autorizada o si no es su turno;
    • líneas 72–75: paso por la ventanilla (lectura de la tabla);
    • líneas 78–79: el lector cambia las condiciones de acceso a la ventanilla de lectura. Todavía posee el token de lectura, y estos cambios impiden que cualquier otro lector acceda a la ventanilla;
    • líneas 81–84: el lector cambia las condiciones de acceso a la ventanilla de escritura y notifica a todos los escritores en espera que algo ha cambiado. Para ello, toma el token [canWrite]: aquí vemos que el hilo posee dos tokens al mismo tiempo. Los escritores hacen lo mismo en orden inverso (poseen [canWrite] y solicitan [canRead]), que es la situación de interbloqueo descrita anteriormente. Sin embargo, aquí no hay riesgo: un hilo solicita el segundo token solo al final de su paso por la ventanilla; las dos ventanillas nunca están ocupadas al mismo tiempo; y los demás hilos poseen un token solo el tiempo necesario para verificar la condición de acceso, sin solicitar el otro token.

Cuando se utiliza una condición de acceso que especifica un hilo en particular, se debe usar [PulseAll].

    8.7. Colecciones concurrentes

    Los ejemplos anteriores protegían datos compartidos muy simples (un contador, un arreglo). Cuando los hilos comparten una colección (lista, diccionario, cola), se podría proteger cada acceso con un [lock]. Pero las colecciones ordinarias ([List<T>], [Dictionary<TKey,TValue>], [Queue<T>]) no están diseñadas para ser modificadas por varios hilos simultáneamente: su uso sin protección puede provocar la pérdida de elementos, desencadenar excepciones inesperadas o incluso corromper la estructura interna de la colección. A partir de .NET 4, el espacio de nombres [System.Collections.Concurrent] ofrece colecciones diseñadas para compartirse entre hilos sin bloqueo explícito:

    Colección
    Función
    [ConcurrentDictionary<TKey,TValue>]
    un diccionario cuyas operaciones, incluidas las actualizaciones condicionales, son seguras
    [ConcurrentQueue<T>]
    una cola (primero en entrar, primero en salir)
    [ConcurrentStack<T>]
    una pila (último en entrar, primero en salir)
    [ConcurrentBag<T>]
    una bolsa: una colección sin orden
    [BlockingCollection<T>]
    un envoltorio de las colecciones anteriores que bloquea al consumidor cuando la colección está vacía y, opcionalmente, al productor cuando está llena

    8.7.2. Productores y consumidores: BlockingCollection

    El problema de lectores y escritores es una variante del problema clásico de productor-consumidor: unos hilos producen datos que otros hilos consumen. La clase [BlockingCollection<T>] lo resuelve sin ninguna herramienta de sincronización explícita:

    • [Add(element)] agrega un elemento. Si la colección tiene una capacidad limitada y está llena, el productor se bloquea hasta que quede un espacio disponible;
    • [CompleteAdding()] señala que no se agregarán más elementos;

    8.8. El grupo de hilos

    Hasta ahora, para gestionar hilos, los hemos creado mediante [new Thread(...)] y luego los hemos ejecutado mediante [Start()]. Crear un hilo es una operación relativamente costosa: en particular, el sistema debe asignarle una pila, y cada hilo ocupa memoria mientras exista. Veremos en el capítulo sobre bases de datos que existen grupos de conexiones: las conexiones abiertas se mantienen en reserva y se prestan a los hilos que las solicitan, ya que abrir una conexión es costoso. Existe un sistema similar para los hilos: el grupo de hilos (ThreadPool) de .NET.

    • Mientras el número de hilos del grupo esté por debajo de un umbral mínimo, el grupo crea de inmediato un nuevo hilo para cada tarea que no encuentra un hilo libre. De forma predeterminada, este mínimo es el número de procesadores; puede leerse mediante [ThreadPool.GetMinThreads(out min1, out min2)] y modificarse mediante [ThreadPool.SetMinThreads(min1, min2)]. El grupo gestiona dos tipos de hilos: los hilos de trabajo (min1), que ejecutan los trabajos que se les asignan, y los hilos de E/S asíncrona (min2);
    • si este número es insuficiente, el grupo crea hilos adicionales de forma incremental, hasta un máximo que puede leerse mediante [ThreadPool.GetMaxThreads(out max1, out max2)] y modificarse mediante [ThreadPool.SetMaxThreads(max1, max2)]. Cuando se alcanza el máximo, los trabajos asignados al grupo se ponen en cola hasta que un hilo quede disponible;
    • Un hilo que ha completado una tarea no se destruye: se devuelve al grupo y se utiliza para la siguiente tarea.

    El grupo de hilos ofrece dos ventajas: ahorra el tiempo dedicado a crear hilos (unos pocos hilos pueden atender cientos de solicitudes) y, al limitar el número de hilos, evita que la aplicación se vea desbordada por demasiadas solicitudes.

    8.10. Datos locales de un hilo

    8.10.1. El principio

    Consideremos una aplicación de tres capas:

    Supongamos que la aplicación es multiusuario, como una aplicación web. Cada solicitud de usuario es atendida por un hilo. El ciclo de vida del hilo es el siguiente:

    • el hilo se crea u obtiene del grupo de hilos para atender la solicitud de un usuario;
    • si esta solicitud requiere datos, el hilo ejecuta un método de la capa [ui], que llama a un método de la capa [business], que a su vez llama a un método de la capa [dao];
    • el hilo devuelve la respuesta al usuario. Luego termina o se devuelve al grupo de hilos.

    Durante el segundo paso, puede ser útil que el hilo tenga sus propios datos, es decir, datos no compartidos con otros hilos. Estos datos podrían, por ejemplo, pertenecer al usuario específico al que el hilo atiende y utilizarse en las diversas capas [ui, business, dao] sin pasarse como parámetro a cada método.

    El curso de 2008 utilizaba los métodos [Thread.SetData] y [Thread.GetData] para este fin, que gestionan una especie de diccionario privado del hilo. Todavía existen, pero se usan poco; se prefieren dos herramientas más sencillas y eficientes:

    • el atributo [[ThreadStatic]] aplicado a un campo estático: cada hilo tiene su propia instancia del campo;
    • la clase [ThreadLocal<T>]: un objeto cuya propiedad [Value] tiene un valor distinto para cada hilo. Una función pasada al constructor proporciona el valor inicial para cada hilo.

    Consideremos la siguiente aplicación de tres capas, en la que la capa [dao] gestiona una tabla de artículos:

    Más adelante surge la necesidad de insertar un arreglo de artículos dentro de una transacción, porque el sistema debe operar bajo el principio de todo o nada: o se insertan todos los artículos, o ninguno. Se puede agregar a la interfaz un método llamado [InsertArticles(Article[] articles)]. Luego, para otra aplicación, surge la necesidad de eliminar una lista de artículos, de nuevo dentro de una transacción… Para satisfacer distintos requisitos de negocio, la capa [dao] irá creciendo. Podemos adoptar un enfoque diferente:

    • incluir solo las operaciones básicas (insertar, actualizar, eliminar, leer un artículo) en la capa [dao];
    • trasladar las operaciones que actualizan simultáneamente varios artículos a la capa [business]. Estas operaciones utilizan las operaciones básicas de la capa [dao].

    La ventaja de esta solución es que la misma capa [dao] puede utilizarse sin modificaciones con distintas capas [business]. Esto introduce un desafío en la gestión de la transacción que agrupa las actualizaciones que deben realizarse de forma atómica:

    • la transacción debe ser iniciada por la capa [business] antes de que esta llame a los métodos de la capa [dao];
    • los métodos de la capa [dao] deben conocer la existencia de la transacción para poder participar en ella;
    • la transacción debe ser finalizada (confirmada o revertida) por la capa [business].

    Para que los métodos de la capa [dao] conozcan cualquier transacción en curso, la transacción podría agregarse como parámetro a cada método de la capa [dao]. Este parámetro aparecería entonces en la firma de los métodos de la interfaz, lo que vincularía la interfaz a una fuente de datos específica. Los datos locales del hilo ofrecen una solución más elegante: la capa [business] coloca la transacción en los datos locales del hilo, y allí es donde la capa [dao] la recupera. // una transacción simulada: registra cómo deshacer cada actualización
class Transaction
{
    private static int counter;
    private readonly Stack<Action> undos = new();
    public int Number { get; } = Interlocked.Increment(ref counter);

    // registra la operación que deshace una actualización
    public void Log(Action undo) => undos.Push(undo);
    // confirma la transacción: se conservan las actualizaciones
    public void Commit() => undos.Clear();
    // revierte la transacción: se deshacen las actualizaciones, de la última a la primera
    public void Rollback()
    {
        while (undos.TryPop(out Action? undo))
        {
            undo();
        }
    }
}

// los datos locales al hilo compartidos por las capas

{
    // la transacción actual del hilo (null si no hay ninguna)
    public static readonly ThreadLocal<Transaction?> Transaction = new();

interface IDao

class Dao : IDao
{
    // la tabla, compartida por todos los hilos, y su bloqueo
    private readonly List<Article> table = [];
    private readonly Lock padlock = new();
    private int nextId = 1;

    public int InsertArticle(Article article)
    {
        // ¿hay una transacción en curso en el hilo actual?
        Transaction? transaction = ThreadContext.Transaction.Value;
        lock (padlock)
        {
            if (table.Any(a => a.Name == article.Name))
            {
                throw new InvalidOperationException($"an article named [{article.Name}] already exists");
            }
            Article inserted = article with { Id = nextId++ };
            table.Add(inserted);
            // dentro de una transacción, se registra cómo deshacer la inserción
            transaction?.Log(() =>
            {
                lock (padlock)
                {
                    table.Remove(inserted);
                }
            });
            string mode = transaction is null ? "outside a transaction" : $"in transaction {transaction.Number}";
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [dao] insertion of {inserted.Name} (id {inserted.Id}) {mode}");
            return 1;
        }
    }

    public List<Article> GetAllArticles()
    {
        lock (padlock)
        {
            return [.. table];
        }
    }

    public void DeleteAllArticles()
    {
        lock (padlock)
        {
            table.Clear();
        }
    }
}

interface IBusiness
{
    void InsertArticlesInTransaction(Article[] articles);
    void InsertArticlesOutOfTransaction(Article[] articles);
    List<Article> GetAllArticles();
    void DeleteAllArticles();
}

class Business(IDao dao) : IBusiness
{
    // inserción de un arreglo de artículos: todo o nada
    public void InsertArticlesInTransaction(Article[] articles)
    {
        // inicio de la transacción, almacenada en los datos locales del hilo
        var transaction = new Transaction();
        ThreadContext.Transaction.Value = transaction;
        try
        {
            foreach (Article article in articles)
            {
                // la capa [dao] encontrará la transacción en el hilo
                dao.InsertArticle(article);
                // procesamiento simulado, que da tiempo a otros hilos para intervenir
                Thread.Sleep(200);
            }
            transaction.Commit();
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [business] transaction {transaction.Number} committed");
        }
        catch
        {
            transaction.Rollback();
            Console.WriteLine($"[{Thread.CurrentThread.Name}] [business] transaction {transaction.Number} rolled back");
            throw;
        }
        finally
        {
            // el hilo ya no tiene una transacción en curso
            ThreadContext.Transaction.Value = null;
        }
    }

    // inserción de un arreglo de artículos sin transacción
    public void InsertArticlesOutOfTransaction(Article[] articles)
    {
        foreach (Article article in articles)
        {
            dao.InsertArticle(article);
        }
    }

    public List<Article> GetAllArticles() => dao.GetAllArticles();
    public void DeleteAllArticles() => dao.DeleteAllArticles();
}

{

    {
        action();

    }
}

    8.10.3. Conclusión

    El ejemplo anterior demostró el valor de los datos locales del hilo para la gestión de transacciones. No debe replicarse tal cual. .NET proporciona este mecanismo de forma nativa con la clase [System.Transactions.TransactionScope]: una transacción «ambiental», accesible mediante [Transaction.Current], en la que las conexiones de base de datos participan automáticamente. Frameworks como Entity Framework Core también gestionan las transacciones sin que el código de la capa [dao] tenga que encargarse de ellas. Y en las aplicaciones web actuales, que son asíncronas, esta información de contexto la transporta [AsyncLocal<T>] en lugar de los datos locales del hilo.

    En el código moderno, rara vez se manipulan directamente objetos [Thread]. En su lugar, se prefieren las tareas ([Task]), ya que se ejecutan en el grupo de hilos, y sobre todo la programación asíncrona mediante las palabras clave [async] y [await], que permite esperar una operación de larga duración (acceso a la red, a una base de datos o a un archivo) sin bloquear un hilo.
