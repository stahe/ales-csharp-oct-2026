    11. Entity Framework Core

    El capítulo anterior mostró cómo una aplicación .NET se comunica con una base de datos a través de un conector ADO.NET: se abre una conexión, se escriben comandos SQL, se leen las filas del resultado columna por columna y se copian en objetos. Este proceso de copia —de filas a objetos y de objetos a los comandos [INSERT], [UPDATE] y [DELETE] — es repetitivo. Se puede automatizar mediante una herramienta: un ORM (Object-Relational Mapper, mapeador objeto-relacional). Este capítulo presenta Entity Framework Core (EF Core) de Microsoft.

    El curso de 2008 no mencionaba los ORM: se limitaba a citar, en la conclusión de su capítulo sobre bases de datos, los “frameworks de acceso a datos de terceros” (NHibernate, iBatis) y LINQ. Entity Framework se lanzó unos meses después (en 2008, con .NET 3.5 SP1) y, en 2012, el autor le dedicó un curso titulado “Introduction to Entity Framework 5 Code First Through Examples”. Este capítulo es completamente nuevo. Se apoya en la base de datos de ejemplo de los artículos del Capítulo 10 y concluye con la versión 7 de la aplicación de cálculo de impuestos, cuya capa [dao] utiliza EF Core.

    11.1. ¿Qué es un ORM?

    11.1.1. Objetos y tablas

    Una aplicación C# trabaja con objetos: un artículo tiene un nombre, un precio y un nivel de existencias; un pedido tiene un cliente y una lista de líneas, cada una de las cuales hace referencia a un artículo. Una base de datos relacional almacena esta misma información en tablas: una fila en la tabla [articles] por artículo, una fila en la tabla [orders] por pedido, con las relaciones entre filas expresadas mediante claves externas. Los dos mundos no coinciden del todo:

    • un objeto hace referencia directamente a otros objetos ([order.Client]); una fila contiene el valor de la clave primaria de otra fila ([ClientId]);
    • un objeto puede contener una colección ([order.Lines]); una tabla solo contiene valores simples; la colección se representa mediante las filas de otra tabla que apuntan al pedido;
    • los tipos de C# ([string], [decimal], [DateOnly], [bool]) y los tipos de SQL ([varchar(30)], [decimal(10,2)], [date], [tinyint(1)]) no son los mismos;
    • los objetos se consultan con C# (y LINQ), y las tablas se consultan con SQL.

    Un ORM tiende un puente entre los dos mundos. Se define de una vez por todas la correspondencia entre clases y tablas (el modelo) y el ORM se encarga de:

    • traducir las consultas LINQ escritas en C# a comandos SQL [SELECT];
    • crear objetos a partir de las filas leídas (esto se denomina materialización);
    • almacenar los objetos leídos y detectar cuáles han sido modificados, agregados o eliminados;
    • generar los comandos [INSERT], [UPDATE] y [DELETE] que reflejan esos cambios en la base de datos;
    • y, si es necesario, crear y actualizar el esquema de la base de datos (tablas, columnas, índices) a partir de las clases.

    La arquitectura de una aplicación que utiliza EF Core con MySQL es la siguiente:

    • [1]: la aplicación. Su capa [dao] ya no se comunica con un conector ADO.NET sino con EF Core, mediante un objeto [DbContext] y consultas LINQ;
    • [2]: EF Core, independiente del SGBD: modelo, traducción de las consultas LINQ, seguimiento de cambios, migraciones;
    • [3]: el proveedor de EF Core específico del SGBD (aquí Pomelo para MySQL): conoce el dialecto SQL del SGBD y sus tipos de columna;
    • [4]: el conector ADO.NET del SGBD, el del Capítulo 10 (MySqlConnector): EF Core no reemplaza a ADO.NET; lo utiliza;
    • [5]: el SGBD.

    11.1.2. EF Core y Entity Framework 6

    Existen dos productos llamados Entity Framework:

    • Entity Framework 6 (EF 6), el producto original, diseñado para .NET Framework en Windows (desde la versión 6.3, también funciona en .NET Core y sus sucesores). Todavía recibe mantenimiento, pero ya no está en desarrollo activo;
    • Entity Framework Core, una reescritura completa lanzada en 2016 con .NET Core. Funciona en todas las plataformas .NET (Windows, Linux, macOS) y es la versión que recibe todas las novedades. Su número de versión sigue al de .NET: EF Core 8 con .NET 8, EF Core 9 con .NET 9, EF Core 10 con .NET 10.

    Para una aplicación nueva, usamos EF Core. Ambos productos tienen API similares ([DbContext], [DbSet<T>], LINQ, migraciones), por lo que lo que se expone aquí sigue siendo válido en gran parte para EF 6.

    11.1.3. Proveedores

    EF Core accede a un SGBD a través de un proveedor, distribuido en un paquete NuGet. Microsoft ofrece los proveedores para SQL Server, SQLite y Azure Cosmos DB; los demás los escriben los editores de los SGBD o la comunidad: [Npgsql.EntityFrameworkCore.PostgreSQL] para PostgreSQL, [Oracle.EntityFrameworkCore] para Oracle, [Pomelo.EntityFrameworkCore.MySql] y [MySql.EntityFrameworkCore] (de Oracle) para MySQL. Utilizamos Pomelo, el proveedor de MySQL más utilizado, que se basa en el conector [MySqlConnector] del Capítulo 10.

    Un proveedor se compila para una versión específica de EF Core: Pomelo 9 funciona con EF Core 9, y las versiones de Pomelo suelen publicarse varios meses después de las de EF Core. El curso utiliza EF Core 9.0.0 y Pomelo 9.0.0, sobre .NET 10. Esta combinación funciona: EF Core 9 tiene como destino .NET 8 ([net8.0]), y una biblioteca compilada para .NET 8 funciona sin modificaciones en .NET 10. El paso a EF Core 10 se logrará cambiando los números de versión de los paquetes; el código de este capítulo debería funcionar entonces sin modificaciones, salvo por algunos detalles menores en el SQL generado. Sin embargo, en la sección sobre LINQ nos encontraremos con una incompatibilidad menor entre EF Core 9 y el compilador de C# 14.

    11.1.4. Code First y Database First

    El modelo de EF Core (la correspondencia entre clases y tablas) puede construirse de dos maneras:

    • Code First: se escriben las clases C# y EF Core deriva de ellas el esquema de la base de datos, que puede crear por sí mismo y luego actualizar a medida que evoluciona la aplicación (migraciones). Este es el enfoque adoptado en este capítulo y en el curso de 2012 del autor;
    • Database First: la base de datos ya existe y se generan las clases a partir de su esquema mediante el comando [dotnet ef dbcontext scaffold]. Este es el enfoque que se utiliza en las aplicaciones que deben trabajar con una base de datos existente. El código generado es similar al que escribiríamos a mano.

// un artículo de la tienda: una clase C# ordinaria, sin vínculo con EF Core
public class Article
{
    // clave primaria (por convención: la propiedad llamada Id)
    public int Id { get; set; }
    // las demás columnas de la tabla
    public string Name { get; set; } = "";
    public decimal Price { get; set; }
    public int CurrentStock { get; set; }
    public int MinimumStock { get; set; }

    // visualización
    public override string ToString() => $"[{Id}, {Name}, {Price}, {CurrentStock}, {MinimumStock}]";
}
    • Línea 4: una clase C# normal. No hereda de ninguna clase de EF Core y no tiene atributos; esto se conoce como un POCO (Plain Old CLR Object);
    • Línea 7: la propiedad [Id] será la clave primaria de la tabla. Esto es una convención de EF Core: una propiedad llamada [Id] (o [ArticleId], el nombre de la clase seguido de [Id]) es la clave primaria. Como es de tipo entero, sus valores serán generados por el SGBD (columna [AUTO_INCREMENT] de MySQL);
    • líneas 9–12: cada propiedad pública de lectura/escritura se convierte en una columna con el mismo nombre. La propiedad [Name] se inicializa con una cadena vacía para satisfacer al compilador (tipos que admiten valores nulos habilitados: una propiedad de tipo [string] no debe quedar en [null]);

    using Microsoft.EntityFrameworkCore;
using Microsoft.Extensions.Logging;

namespace First;

// el contexto: la puerta de acceso a la base de datos [efarticles]
public class ArticlesContext : DbContext
{
    // la tabla de artículos
    public DbSet<Article> Articles => Set<Article>();

    // configuración del contexto: DBMS, cadena de conexión, registro
    protected override void OnConfiguring(DbContextOptionsBuilder options)
    {
        const string connection = "Server=localhost;Port=3306;Database=efarticles;User=root;Password=";
        options
            // el proveedor de MySQL y la versión del servidor
            .UseMySql(connection, new MySqlServerVersion(new Version(8, 0, 36)))
            // muestra de las sentencias SQL enviadas al servidor
            .LogTo(Console.WriteLine, [DbLoggerCategory.Database.Command.Name], LogLevel.Information);
    }
}
    • Línea 7: la clase [DbContext] proviene de EF Core. Un objeto [ArticlesContext] representa una sesión de trabajo con la base de datos: abre la conexión cuando es necesario, almacena las entidades que ha leído y puede guardar los cambios realizados en ellas;
    • Línea 10: un [DbSet<Article>] representa la tabla de artículos. Aquí se ejecutan las consultas LINQ y se agregan o eliminan artículos. La propiedad se define como un miembro con cuerpo de expresión que llama a [Set<Article>()]: cada [DbSet<T>] declarado en el contexto introduce el tipo [T] en el modelo;
    • línea 13: EF Core llama al método [OnConfiguring] la primera vez que se utiliza el contexto, para configurarlo;
    • línea 15: la cadena de conexión, la misma que en el Capítulo 10: servidor, puerto, base de datos, nombre de usuario y contraseña (vacía para el usuario [root] de Laragon);
    • línea 18: el contexto utiliza el proveedor Pomelo. El segundo parámetro especifica la versión del servidor MySQL: el SQL generado depende de ella, ya que ciertas funcionalidades solo están disponibles en versiones recientes. Laragon proporciona MySQL 8; especificamos la versión 8.0.36. Pomelo también ofrece [ServerVersion.AutoDetect(connection)], que consulta al servidor para determinar su versión. Esto es cómodo, pero implica una conexión adicional cada vez que se configura un contexto, y el SQL generado pasa a depender del servidor encontrado. Especificar una versión de forma explícita hace que el comportamiento de la aplicación sea reproducible;
    • línea 20: el método [LogTo] indica a EF Core que escriba su registro mediante el método [Console.WriteLine]. Conservamos únicamente la categoría de mensajes [DbLoggerCategory.Database.Command] —la de los comandos SQL ejecutados— en el nivel [LogLevel.Information]. Sin este filtro, el registro es muy detallado. Ver el SQL enviado al servidor es la mejor manera de comprender lo que hace EF Core: lo haremos en todos los ejemplos.

    using First;

// un contexto de EF Core: se liberará (conexión incluida) al final del programa
using var context = new ArticlesContext();

// la base de datos se elimina y luego se vuelve a crear a partir del modelo C#
context.Database.EnsureDeleted();

// adición de tres artículos

context.Articles.Add(new Article { Name = "bow", Price = 600, CurrentStock = 4, MinimumStock = 1 });

    11.3. El modelo

    EF Core construye su modelo a partir de las entidades en tres pasos:

    • primero, aplica sus convenciones;
    • las complementa o corrige mediante las anotaciones (atributos) aplicadas a las entidades;
    • por último, aplica la configuración escrita en C# en el método [OnModelCreating] del contexto: la API fluida.

    11.3.1. Las convenciones

    Vimos lo esencial de ellas en el primer ejemplo:

    • toda propiedad pública con un getter [get] y un setter [set] (o [init]) se almacena en una columna del mismo nombre;
    • la propiedad [Id] o [<Entity>Id] es la clave primaria; si es un entero, sus valores los genera el SGBD;
    • el nombre de la tabla es el de la propiedad [DbSet] del contexto (o, en su defecto, el de la clase);
    • una propiedad de un tipo que admite valores nulos ([int?], [DateOnly?], [string?]) da lugar a una columna [NULL]; una propiedad de un tipo que no admite valores nulos ([int], [decimal], [string] cuando los tipos de referencia que admiten valores nulos están habilitados) da lugar a una columna [NOT NULL];
    • una propiedad que hace referencia a otra entidad, o una colección de entidades, define una relación (la trataremos más adelante).

    11.3.3. Tipos que admiten valores nulos y columnas NULL

    Los tipos de referencia que admiten valores nulos (C# 8, habilitados mediante [<Nullable>enable</Nullable>] en los proyectos del curso) tienen un impacto en el modelo: EF Core lee las anotaciones de nulabilidad generadas por el compilador. Una propiedad [string] da lugar a una columna [NOT NULL], y una propiedad [string?] da lugar a una columna [NULL]. En un proyecto donde los tipos que admiten valores nulos no están habilitados, todas las columnas de texto aceptan [NULL], salvo las marcadas con [Required].

    Por lo tanto, hay que elegir con cuidado el tipo de cada propiedad: expresa a la vez una regla del código C# (“este valor puede faltar”) y una restricción de la base de datos. Para una propiedad obligatoria, son comunes dos notaciones:

namespace Ef.Tools;

// un registro compacto de las sentencias SQL ejecutadas por EF Core
public static class SqlLog
{
    // un miembro de extensión (C# 14) del tipo DbContextOptionsBuilder
    extension(DbContextOptionsBuilder options)
    {
        // options.WithSqlLog(): muestra cada sentencia SQL ejecutada
        public DbContextOptionsBuilder WithSqlLog() => options.LogTo(Filter, Display);
    }

    // los eventos seleccionados: comando SQL ejecutado o fallido, inicio y fin de las transacciones
    private static bool Filter(EventId id, LogLevel level) =>
        id == RelationalEventId.CommandExecuted || id == RelationalEventId.CommandError
        || id == RelationalEventId.TransactionStarted
        || id == RelationalEventId.TransactionCommitted || id == RelationalEventId.TransactionRolledBack;

    // muestra de un evento
    private static void Display(EventData data)
    {
        switch (data)
        {
            case CommandExecutedEventData command:
                DisplayCommand(command.Command);
                break;
            case CommandErrorEventData error:
                DisplayCommand(error.Command);
                Console.WriteLine("    SQL> -- command failed");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionStarted:
                Console.WriteLine("    SQL> -- start of transaction");
                break;
            case TransactionEventData when data.EventId == RelationalEventId.TransactionCommitted:
                Console.WriteLine("    SQL> -- transaction committed (COMMIT)");
                break;
            case TransactionEventData:
                Console.WriteLine("    SQL> -- transaction rolled back (ROLLBACK)");
                break;
        }
    }

    // muestra de la sentencia SQL, con sangría, y luego de sus parámetros
    private static void DisplayCommand(DbCommand command)
    {
        // las líneas vacías se ignoran
        foreach (string line in command.CommandText.Split('\n').Select(l => l.TrimEnd()).Where(l => l != ""))
        {
            Console.WriteLine("    SQL> " + line);
        }
        if (command.Parameters.Count > 0)
        {
            var parameters = command.Parameters.Cast<DbParameter>()
                .Select(p => $"{(p.ParameterName.StartsWith('@') ? "" : "@")}{p.ParameterName}={p.Value}");
            Console.WriteLine($"    SQL> -- parameters: {string.Join(", ", parameters)}");
        }
    }
}

    • el comando [INSERT], seguido de un [SELECT] de la clave generada, está encerrado dentro de una transacción (líneas 13–20): el comando contiene dos comandos SQL que deben tener éxito juntos. Volveremos sobre las transacciones más adelante;

Este ajuste no tiene efecto sobre una transacción abierta de forma explícita, como veremos.

    11.5.2. Los estados de una entidad

    El seguimiento de cambios se basa en el estado de cada entidad, un valor de la enumeración [EntityState]:

    Estado
    Significado
    [Detached]
    El contexto no sigue al objeto (creado con [new] y aún no agregado, o eliminado de la base de datos)
    [Added]
    El objeto se ha agregado al contexto ([Add]): [SaveChanges] lo insertará en la base de datos
    [Unchanged]
    El objeto se leyó de la base de datos (o se guardó) y no se ha modificado desde entonces
    [Modified]
    Se ha modificado al menos una propiedad: [SaveChanges] enviará un comando [UPDATE]
    [Deleted]
    El objeto se ha marcado para su eliminación ([Remove]): [SaveChanges] enviará un comando [DELETE]

    Observe el ciclo de trabajo con EF Core: se leen entidades, se modifican como objetos ordinarios, se agregan y se eliminan, y luego se llama a [SaveChanges], que envía todos los comandos necesarios a la base de datos en un solo lote. El contexto actúa como una “unidad de trabajo”. Un contexto es un objeto ligero diseñado para tener una vida corta: una unidad de trabajo, como una solicitud HTTP en una aplicación web. No se utiliza el mismo contexto durante toda la vida de una aplicación, ya que acumularía entidades bajo seguimiento.

    11.6.2. IQueryable y árboles de expresión

    ¿Cómo puede ejecutarse la misma lambda en C# sobre una lista y traducirse a SQL sobre un [DbSet]? El Capítulo 7 dio la respuesta: un [DbSet<T>] implementa la interfaz [IQueryable<T>], cuyos métodos [Where], [OrderBy], [Select]... no reciben delegados ([Func<T, bool>]) sino árboles de expresión ([Expression<Func<T, bool>>]). El compilador transforma la lambda [a => a.CurrentStock < a.MinimumStock] en una estructura de datos que la describe (“ comparación [<] de la propiedad [CurrentStock] y la propiedad [MinimumStock] del parámetro [a]”); EF Core recorre esta estructura y produce el SQL equivalente. Un método como [Rules.OutOfStock] aparece en el árbol solo como una llamada a método, cuyo código no puede analizarse: de ahí el error.

    Los operadores se componen: una consulta puede construirse por etapas, devolviendo cada etapa un nuevo [IQueryable<T>], y solo la ejecución final ([ToList], [First], [Count], [foreach]...) envía un comando SQL:

    11.6.3. Una incompatibilidad entre EF Core 9 y C# 14

    En el programa [Linq], la lista [names] se declaró de tipo [List<string>] en lugar de [string[]], con un comentario que hace referencia a este párrafo. Con un arreglo, la consulta [context.Articles.Where(a => names.Contains(a.Name))] se compila, pero falla en tiempo de ejecución con un error [InvalidOperationException] (“An exception was thrown while attempting to evaluate a LINQ query parameter expression”). En efecto, C# 14 ha convertido la conversión de un arreglo a [ReadOnlySpan<T>] (el tipo presentado en el Capítulo 5) en una conversión implícita del lenguaje, que se aplica también al objeto sobre el que se llama a un método de extensión. Para un arreglo, la llamada [names.Contains(...)] ahora hace referencia, por lo tanto, al método de extensión [MemoryExtensions.Contains(ReadOnlySpan<T>, T)] en lugar de a [Enumerable.Contains(IEnumerable<T>, T)]: esto se evidencia al examinar el árbol de expresión de la lambda, y el mismo programa compilado en C# 13 ([<LangVersion>13</LangVersion>]) encuentra [Enumerable.Contains] y funciona. EF Core 9, publicado antes que C# 14, no reconoce este método: intenta evaluar la conversión del arreglo a [ReadOnlySpan<string>] para convertirla en un parámetro SQL, lo que falla (la excepción interna es una [ArgumentException] lanzada por el intérprete de árboles de expresión). EF Core 10, publicado junto con C# 14, admite esta sintaxis. Con EF Core 9, se puede sortear el problema utilizando una lista, como se muestra aquí, o escribiendo [((IEnumerable<string>)names).Contains(a.Name)]. Este es el único problema encontrado en este capítulo al usar EF Core 9 con .NET 10.

Supongamos que queremos mostrar el nombre del cliente de cada pedido y leemos los pedidos sin [Include], y luego recuperamos el cliente de cada uno mediante una carga explícita (o una carga diferida, que equivale a lo mismo sin que nos demos cuenta): ejecutamos una consulta para los N pedidos y luego N consultas, una por pedido. Las soluciones son las que se muestran en el ejemplo: [Include] o, mejor aún, una proyección ([Select]) que recupere únicamente los datos pertinentes. El registro SQL ayuda a identificar el problema: la misma consulta repetida numerosas veces.

    11.8. Migraciones

    11.8.1. El principio

    Hasta ahora, la base de datos se ha creado con [EnsureCreated], tras ser eliminada con [EnsureDeleted]. Esto es imposible en una aplicación en producción: su base de datos contiene datos que deben conservarse cuando el modelo evoluciona (una nueva columna, una nueva tabla). Además, [EnsureCreated] solo puede crear una base de datos que no existe: si la base de datos ya existe con tablas, no hace nada, aunque el modelo haya cambiado.

    Las migraciones responden a esta necesidad. Una migración es una clase C#, generada por la herramienta [dotnet ef], que describe la transición de una versión del modelo a la siguiente: su método [Up] aplica el cambio (crear una tabla, agregar una columna), mientras que su método [Down] lo revierte. La base de datos contiene una tabla llamada [__EFMigrationsHistory], en la que EF Core registra las migraciones que se le han aplicado; esto le permite saber cuáles faltan por aplicar.

    11.10. Transacciones y concurrencia

    11.10.1. Transacciones

    El capítulo 10 presentó las transacciones: un conjunto de operaciones que se completan todas o fallan todas. Con EF Core, hay dos puntos clave que tener en cuenta:

    11.10.2. Concurrencia optimista

    Dos usuarios leen el mismo artículo, que tiene un stock de 10. El primer usuario vende uno y actualiza el stock a 9. El segundo usuario, que leyó el stock antes de esta actualización, vende tres y actualiza el stock a 7: la venta del primer usuario se pierde. Este es el problema de las actualizaciones perdidas.

    Una solución sería bloquear la fila durante toda la operación de cada usuario (concurrencia «pesimista»): esto bloquea a los demás usuarios, a veces durante mucho tiempo. EF Core implementa la concurrencia optimista: no se bloquea nada, pero en el momento de la confirmación, el sistema verifica que la fila no haya sido modificada desde que se leyó. Para ello, se designan una o más propiedades como tokens de concurrencia: EF Core agrega la condición «el token todavía tiene el valor leído» a la cláusula [WHERE] de las instrucciones [UPDATE] y [DELETE] . Si el comando no modifica ninguna fila, significa que otro usuario ya las procesó: EF Core lanza una [DbUpdateConcurrencyException].

    11.12. Contexto e inyección de dependencias

    Los ejemplos anteriores creaban sus contextos con [new]. En una aplicación por capas, y en todas las aplicaciones ASP.NET Core, los contextos los crea el contenedor de inyección de dependencias presentado en el capítulo 6. EF Core ofrece dos métodos de extensión de [IServiceCollection] para este fin:

    • [AddDbContext<T>(options => ...)] registra el contexto [T] con un ciclo de vida «con ámbito» (scoped): el contenedor crea un contexto por ámbito, lo proporciona a todos los servicios de ese ámbito que lo soliciten y lo libera al final del ámbito. En una aplicación web, se crea un ámbito por cada solicitud HTTP: cada solicitud tiene su propio contexto, lo que corresponde a la unidad de trabajo del contexto;
    • [AddDbContextFactory<T>(options => ...)] registra una fábrica de contextos, [IDbContextFactory<T>], cuyo método [CreateDbContext] crea un contexto nuevo en cada llamada. Se usa en servicios de larga duración (singletons), que no pueden mantener el mismo contexto durante toda la vida de la aplicación, y en el procesamiento en paralelo, que requiere un contexto por tarea.

    En ambos casos, la lambda recibe un [DbContextOptionsBuilder] y configura el contexto como lo hacía [OnConfiguring]; el contexto debe tener un constructor que acepte un [DbContextOptions<T>], como el de la clase [ArticlesContext] .

    11.14. Conclusión: ¿ADO.NET, Dapper o EF Core?

    Ahora tenemos dos maneras de acceder a una base de datos: ADO.NET (capítulo 10) y EF Core (este capítulo). Existe una tercera, intermedia y muy utilizada: Dapper, una pequeña biblioteca (un «micro-ORM») que agrega métodos de extensión a la conexión ADO.NET. Estos métodos ejecutan una consulta SQL escrita a mano y convierten automáticamente las filas del resultado en objetos: [connection.Query<Article>("SELECT * FROM articles WHERE Price > @price", new { price = 200 })]. Usted escribe el SQL y Dapper se encarga de asignar las columnas a las propiedades.

     
    Fortalezas
    Debilidades
    ADO.NET
    Control total sobre el SQL; rendimiento; sin dependencias
    mucho código repetitivo (parámetros, lectura de columnas); SQL en cadenas, no verificado por el compilador
    Dapper
    SQL escrito a mano, pero sin el código de copia; rendimiento similar al de ADO.NET
    Sin seguimiento de cambios ni generación de [INSERT]/[UPDATE]; sin migraciones
    EF Core
    Consultas LINQ verificadas por el compilador; seguimiento de cambios; relaciones; migraciones; independiente del SGBD
    una capa adicional que comprender; SQL generado que hay que monitorear; menos adecuado para procesamientos masivos complejos

    Se pueden proponer las siguientes pautas:

    • EF Core es adecuado para la mayoría de las aplicaciones de gestión: un modelo de entidades interrelacionadas, operaciones de lectura y actualización de entidades y un esquema que evoluciona con la aplicación. Es la opción predeterminada para las aplicaciones ASP.NET Core;
    • ADO.NET, o Dapper, es adecuado cuando se desea un control preciso sobre el SQL ejecutado: consultas de informes complejas, procedimientos almacenados, procesamiento de volúmenes muy grandes o una base de datos existente con un esquema poco adecuado para un modelo orientado a objetos;
    • Estos enfoques pueden combinarse: una aplicación puede usar EF Core para la mayor parte y código SQL escrito a mano (con [FromSql], [SqlQuery] o Dapper) para unas pocas consultas críticas. EF Core también da acceso a la conexión ADO.NET que utiliza ([context.Database.GetDbConnection()]).

    En cualquier caso, conocer el ORM no elimina la necesidad de entender SQL y el funcionamiento del SGBD: el registro de los comandos SQL ejecutados, que hemos mostrado a lo largo de este capítulo, es la herramienta principal para verificar lo que EF Core realmente hace.

    Para obtener más información, la documentación de Microsoft es completa: Entity Framework Core. El proveedor Pomelo está documentado en su repositorio: Pomelo.EntityFrameworkCore.MySql.
