    7. Delegados, lambdas y eventos

    En el curso de 2008, este capítulo seguía al de las interfaces gráficas de usuario con Windows Forms: los eventos se presentaban primero en el contexto de los botones y los formularios, y luego los estudiantes aprendían a crear eventos en sus propias clases. El capítulo sobre interfaces gráficas de usuario se ha eliminado de esta versión del curso. Por lo tanto, comenzamos directamente con el concepto que sustenta todo el mecanismo: el delegado, es decir, un objeto que hace referencia a uno o más métodos. Todos los ejemplos son programas de consola.

    En los últimos veinte años, los delegados se han convertido en una de las herramientas más utilizadas del lenguaje. Escribirlos se ha vuelto considerablemente más sencillo con las expresiones lambda (C# 3), que ya hemos usado, sin entrar en detalles, con LINQ en el capítulo 5: [Where(n => n > 5)] pasa una lambda (y, por lo tanto, un delegado) al método [Where]. Este capítulo explica qué hay detrás de esta sintaxis. Concluye con los eventos, que también se basan en delegados. Las interfaces gráficas de usuario de .NET (Windows Forms, WPF, .NET MAUI), así como los frameworks web, se basan en este mecanismo: un clic en un botón o la llegada de una solicitud HTTP se señalan a los métodos suscritos.

    Los programas de este capítulo son aplicaciones de archivo único ubicadas en la carpeta [07-delegates]. Se ejecutan con [dotnet run delegates-NN.cs].

    7.1. Tipos de delegado predefinidos

    7.1.1. El concepto de delegado

    Un tipo de delegado describe un modelo (también llamado prototipo o firma) de un método: los tipos de sus parámetros y el tipo de su valor de retorno. Una variable de un tipo de delegado puede entonces hacer referencia a cualquier método que se ajuste a este modelo y ejecutarlo.

    .NET define numerosos tipos de delegado. El más antiguo es [EventHandler], utilizado por todos los eventos que veremos al final de este capítulo. Se define de la siguiente manera:

    1
    public delegate void EventHandler(object? sender, EventArgs e);

    La palabra clave [delegate] convierte a [EventHandler] en un tipo de delegado. Este tipo designa un patrón de método:

    • cuyo primer parámetro es un objeto de tipo [object?] (el objeto que desencadenó el evento, posiblemente [null]);
    • cuyo segundo parámetro es un objeto de tipo [EventArgs] (información sobre el evento);
    • que no devuelve ningún resultado ([void]).

    Un método que corresponda al modelo definido por [EventHandler] podría ser el siguiente:

    1
    static void Display(object? sender, EventArgs e) { ... }

    Para crear un objeto de tipo [EventHandler] que haga referencia a este método, se puede escribir:

    1
    EventHandler handler = new EventHandler(Display);

    o, de forma más simple:

    1
    EventHandler handler = Display;

    En esta segunda notación, el nombre del método [Display] (un grupo de métodos, ya que un método puede tener varias sobrecargas) es convertido automáticamente por el compilador en un objeto [EventHandler]: es la conversión de grupo de métodos, posible desde C# 2. El compilador selecciona, entre las sobrecargas de [Display], la que coincide con la firma del delegado. Luego el delegado se ejecuta como un método: [handler("program", EventArgs.Empty)].

    7.1.2. Los delegados genéricos Func, Action y Predicate

    Antes de los genéricos (C# 2), había que definir un tipo de delegado para cada firma de método. Hoy, el framework proporciona tipos de delegado genéricos que cubren casi todas las necesidades:

    Tipo de delegado
    Métodos referenciados
    [Action]
    Sin parámetros, sin valor de retorno: [void M()]
    [Action<T1, ..., T16>]
    De 1 a 16 parámetros, sin resultado: [void M(T1 p1, ...)]
    [Func<TResult>]
    Sin parámetros, un resultado: [TResult M()]
    [Func<T1, ..., T16, TResult>]
    De 1 a 16 parámetros, un resultado del tipo [TResult] (siempre el último tipo)
    [Predicate<T>]
    un parámetro, un resultado booleano: [bool M(T p)]
    [Comparison<T>]
    dos parámetros del mismo tipo, un resultado entero: [int M(T x, T y)]

    [Predicate<T>] y [Func<T, bool>] describen la misma firma, pero son dos tipos distintos: [Predicate<T>] data de .NET 2 y es utilizado por los métodos de [List<T>] y [Array] ([FindAll], [RemoveAll], [Exists]…), mientras que LINQ, introducido con .NET 3.5, usa [Func<T, bool>].

    7.2. Definición de tipos de delegado

    Los tipos predefinidos suelen ser suficientes, pero es posible definir tipos de delegado propios. La instrucción:

    1
    public delegate int Operation(int n1, int n2);

    define un tipo llamado [Operation], que representa una plantilla de método que recibe dos enteros y devuelve un entero. En comparación con [Func<int, int, int>], el tipo [Operation] tiene un nombre que describe su propósito, y sus parámetros tienen nombres ([n1], [n2]) que las herramientas de desarrollo muestran.

    Una variable [op] de tipo [Operation] se usa para almacenar una lista de métodos que corresponden al modelo [Operation]: esto se denomina delegado multidifusión (multicast).

    • Un método de tipo [f] se almacena en la variable [op] mediante [op = new Operation(f)] o, más simplemente, [op = f];
    • Para agregar un método [g] a la lista de métodos ya registrados, se escribe [op += g];
    • Para quitar un método [h] que ya está registrado, se escribe [op -= h];
    • La instrucción [n = op(n1, n2)] ejecuta, en el orden en que fueron registrados, todos los métodos registrados en [op], con los parámetros [n1] y [n2]. El resultado devuelto [n] es el del último método ejecutado.

    El curso de 2008 indicaba que no es posible obtener los resultados de todos los métodos. Sí es posible, pero no con una sola llamada: hay que recorrer la lista de métodos devuelta por [GetInvocationList] y llamarlos uno por uno. En la práctica, los métodos registrados en un delegado de multidifusión devuelven casi siempre [void].

Operation op = Calculations.Increase;

// registramos el método Subtract de c1 en el delegado

// registro de dos métodos en el delegado (delegado multidifusión)
op = c1.Add;
op += c1.Subtract;
// ejecución del objeto delegado: obtenemos el resultado del último método
n = op(10, 4);
Console.WriteLine($"n={n}");
// los resultados de todos los métodos con la lista de invocación
foreach (Operation method in op.GetInvocationList().Cast<Operation>())
{
    Console.WriteLine($"{method.Method.Name} -> {method(10, 4)}");
}
// quitamos un método del delegado: el resultado puede ser null (tipo Operation?)
Operation? rest = op - c1.Subtract;
// ejecutamos el delegado si no es null
if (rest is not null)
{
    n = rest(1, 1);
    Console.WriteLine($"n={n}");
}
// quitamos el último método: el delegado pasa a ser null
Operation? empty = rest - c1.Add;
Console.WriteLine($"empty is null: {empty is null}");
// ?.Invoke ejecuta el delegado solo si no es null
Console.WriteLine($"empty?.Invoke(1, 1)={empty?.Invoke(1, 1)}");

El resultado del operador [-] es de tipo [Operation?]: si se quita el último método de un delegado, se obtiene [null]*, no un delegado vacío. El compilador, que hace seguimiento de los tipos que admiten valores nulos (véase el capítulo 3), emitiría advertencias si se escribiera [op -= c1.Subtract] seguido de [op(1, 1)]: [CS8601] al asignar un valor potencialmente nulo a la variable que no admite valores nulos [op], y [CS8602] al llamar al método. Por eso almacenamos el resultado en una variable de tipo [Operation?] y lo verificamos antes de ejecutarlo (línea 36);

La interpolación de cadenas representa [null] como una cadena vacía. Volveremos a ver esta sintaxis al tratar los eventos.

    Un delegado es un objeto inmutable: las operaciones [+] y [-] (y, por lo tanto, [+=] y [-=]) no modifican el delegado existente; crean uno nuevo. Esta propiedad será importante al tratar los eventos.

// 1 - un método anónimo (C# 2): el cuerpo del método se escribe en el lugar

};

{

};

// 3 - los tipos de los parámetros se infieren del tipo de delegado de destino
Func<int, int, int> multiply = (n1, n2) => n1 * n2;

// 4 - un solo parámetro: los paréntesis son opcionales
Func<int, int> square = x => x * x;
Predicate<string> isEmpty = s => s.Length == 0;

// 5 - sin parámetros: paréntesis vacíos
Func<string> greet = () => "Hello";

beep();

// 6 - un cuerpo en bloque con varias instrucciones
Action<string, int> repeat = (text, times) =>

    }
    Console.WriteLine();

El cuerpo se reduce a una expresión, cuyo valor es el resultado de la lambda: es una lambda con cuerpo de expresión (lambda expression). Esta es la forma más común;
    • línea 22: con un único parámetro cuyo tipo no se especifica, los paréntesis son opcionales. [x => x * x] se lee “x da x por x”. Línea 23: la misma lambda de un solo parámetro, de tipo [string], devuelve un valor booleano: es un [Predicate<string>];
    • Líneas 27–28: sin parámetros, se usan paréntesis vacíos. Una lambda cuyo cuerpo es una llamada a un método ([void]) es adecuada para un delegado ([Action]);
    • líneas 33–39: una lambda con cuerpo de bloque puede contener cualquier instrucción: declaraciones, bucles, condicionales, etc.;
    • línea 44: el carácter de subrayado [_] denota un parámetro ignorado (descarte, C# 9). Se usa cuando la firma del delegado exige parámetros que la lambda no necesita, lo cual es habitual en los controladores de eventos;
    • línea 49: el uso más común de las lambdas es pasarlas directamente como parámetros a un método que espera un delegado. Compárese con [delegates-01.cs]: ya no es necesario escribir un método [IsEven];
    • línea 50: una lambda de tipo [Comparison<int>] que invierte la comparación habitual: la lista se ordena de forma descendente.

    Repasemos las formas de una expresión lambda:

    Forma
    Ejemplo
    parámetros con tipo, cuerpo de bloque
    [(int a, int b) => { return a + b; }]
    parámetros sin tipo, cuerpo de expresión
    [(a, b) => a + b]
    un único parámetro sin tipo
    [x => x * x]
    sin parámetros
    [() => "Hello"]
    parámetros ignorados
    [(_, _) => Console.WriteLine("received")]

    Los parámetros son todos con tipo o todos sin tipo: no se pueden mezclar. En este curso usaremos lambdas en lugar de métodos anónimos, que hoy solo son útiles en casos poco frecuentes.

    7.5. Gestión de eventos

    7.5.1. El modelo de eventos de .NET

    Los delegados se utilizan para definir eventos. Una clase [C1] puede definir un evento [Evt1] de la siguiente manera:

    • Se define un tipo delegado dentro o fuera de la clase [C1]:
    1
    delegate void Evt(T1 param1, T2 param2, ...);
    • La clase [C1] define un campo de este tipo delegado:
    1
    public Evt? Evt1;
    • Cuando una instancia [c1] de la clase [C1] quiere señalar un evento, ejecuta su delegado [Evt1] pasándole los parámetros definidos por el tipo [Evt]. Todos los métodos registrados en el delegado [Evt1] se ejecutan entonces con esos parámetros. Se dice que han sido notificados del evento [Evt1];
    • si un objeto [c2] que utiliza el objeto [c1] quiere ser notificado del evento [Evt1] del objeto [c1], registra uno de sus métodos, [c2.M], en el delegado [c1.Evt1]. Su método [c2.M] se ejecutará entonces cada vez que el evento [Evt1] ocurra en el objeto [c1]. También puede cancelar su suscripción cuando ya no desee ser notificado;
    • como el delegado [c1.Evt1] puede registrar varios métodos, distintos objetos [ci] pueden registrarse en [c1.Evt1] para ser notificados del evento.

    En este escenario, tenemos:

    • una clase que señala (también se dice "publica" o "emite") un evento;
    • clases que son notificadas de este evento. Se dice que están suscritas al evento;
    • un tipo delegado que define la firma de los métodos que serán notificados del evento. Estos métodos se denominan controladores de eventos.

    Este es el patrón de diseño Observador (Observer): el emisor no conoce a sus suscriptores; simplemente los notifica.

    El framework .NET define una firma estándar para un delegado de evento:

    1
    public delegate void MyEventHandler(object? sender, EventArgs e);
    • [sender]: el objeto que desencadenó el evento;
    • [e]: un objeto de tipo [EventArgs] o de un tipo derivado, que proporciona información sobre el evento;
    • Por convención, el nombre del tipo delegado termina en [EventHandler].

    También define una forma estándar de declarar en una clase un evento de tipo [MyEventHandler] :

    1
2
3
4
5
    public class C1
{
    public event MyEventHandler? Evt1;
    ...
}

    El campo [Evt1] es del tipo delegado. La palabra clave [event] restringe las operaciones que se pueden realizar sobre él:

    • Desde fuera de la clase [C1], solo se permiten las operaciones [+=] y [-=]. Esto impide que otros objetos sobrescriban o eliminen los métodos suscritos (por error, por ejemplo, al escribir [=] en lugar de [+=]). Solo se puede suscribir ([+=]) o cancelar la suscripción ([-=]);
    • solo la clase [C1] puede ejecutar el delegado, es decir, desencadenar el evento: [Evt1?.Invoke(this, e)].

    Si se intenta, desde fuera de la clase, escribir [c1.Evt1 = null;] o [c1.Evt1(null, EventArgs.Empty);], el compilador responde con: [error CS0070: The event 'C1.Evt1' can only appear on the left hand side of += or -= (except when used from within the type 'C1')].

    En lugar de definir un tipo delegado para cada evento, se utiliza el delegado genérico predefinido:

    1
    public delegate void EventHandler<TEventArgs>(object? sender, TEventArgs e);

    El tipo [TEventArgs] es el del segundo parámetro, el objeto que describe el evento. Con este delegado genérico, la declaración de un evento [X] en una clase [C] sigue el patrón recomendado a continuación:

    • definir un tipo [XEventArgs] derivado de [EventArgs] para encapsular la información sobre el evento [X];
    • definir un evento de tipo [EventHandler<XEventArgs>] en la clase [C];
    • definir en la clase [C] un método protegido y virtual [protected virtual void OnX(XEventArgs e)] destinado a publicar el evento [X] a los suscriptores. Es virtual para que una clase derivada pueda modificar la forma en que se publica el evento.

    En 2008, el tipo [TEventArgs] debía derivar de [EventArgs] (restricción [where TEventArgs : EventArgs]). Esta restricción se eliminó en .NET Framework 4.5: cualquier tipo es aceptable, incluido un [record]. Sin embargo, por convención, se sigue derivando de [EventArgs]. Tenga en cuenta que un [record] no puede derivar de [EventArgs]: un [record] solo puede heredar de otro [record] (error: [CS8864: Records may only inherit from object or another record]). Por lo tanto, utilizaremos una clase normal.

public class Subscriber(string name, int nbAlertsMax)

public static class Tools
{
    // filtra una secuencia con un predicado: el equivalente de Where
    public static IEnumerable<T> Filter<T>(IEnumerable<T> source, Func<T, bool> predicate)
    {
        foreach (T element in source)
        {
            if (predicate(element))
            {
                // el elemento se devuelve al llamador; la iteración continuará aquí
                yield return element;
            }
        }
    }
}

public static class Extensions
{
    // miembros de extensión (C# 14) de IEnumerable<T>
    extension<T>(IEnumerable<T> source)
    {
        // Filter como método de extensión: reutilizamos Tools.Filter
        public IEnumerable<T> Filter(Func<T, bool> predicate) => Tools.Filter(source, predicate);

        // transforma cada elemento: el equivalente de Select
        public IEnumerable<TResult> Transform<TResult>(Func<T, TResult> transformation)
        {
            foreach (T element in source)
            {
                yield return transformation(element);
            }
        }
    }
}

La misma lambda, escrita de la misma manera, se convierte así en código .NET o en código SQL, según el tipo del parámetro que reciba.

    7.8. Conclusión

    Puntos clave de este capítulo:

    • Un delegado es un objeto que hace referencia a uno o varios métodos con una firma determinada. Los tipos predefinidos [Func<>], [Action<>], y [Predicate<T>] suelen eliminar la necesidad de definir tipos delegados propios;
    • las expresiones lambda permiten escribir el método justo donde se crea el delegado. Capturan las variables que las rodean (cuidado con los bucles [for]);
    • Un delegado puede reemplazar a una interfaz de un solo método, con mayor flexibilidad;
    • un evento es un delegado protegido por la palabra clave [event]: uno se suscribe con [+=], cancela la suscripción con [-=], y solo la clase que lo declara lo desencadena, mediante [Evt?.Invoke(this, e)];
    • LINQ se basa en métodos que aceptan delegados, y EF Core se basa en árboles de expresión.
